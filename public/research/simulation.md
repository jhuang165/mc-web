# Simulation boundary

SIM-01 has begun with `tickBlockSystems` in `src/world-tick.js`. The live player tick passes its current time, daylight and player X/Z to this browser-independent function. It advances farming, fluids and fire in that order and invokes each supplied observer immediately after its system runs. The live observers rebuild farm chunks and apply fluid/fire changes to the scene. A headless caller can supply its own observers.

`src/world-tick.test.js` runs 70 changing input ticks through the previous call sequence and the extracted function with real World, Farming, Fluids, Fire and shared Weather random state. It compares ordered observer results, blocks, farmland state, pending queues and random state on every tick; scheduled water changes and fire random draws are exercised. This is a port regression, not an original Java integrated-tick comparison.

`src/weather-simulation.js` advances the existing weather and lightning damage logic without a scene or sound dependency. The live caller invokes client rain particles and drains sound events afterward. Tests use real lightning bolts to cover repeated flashes, mob/player ordering, fire counters, powered creepers, edge contact and Creative/dead exclusions. A 160-tick headless run combines weather and block steps, saving and restoring their existing browser snapshots five times while comparing ordered changes, farmland, queues and shared random state. It uses clear weather without active lightning at reload; it does not establish active-bolt or weather-strength continuity.

`src/player-input.js` captures movement keys as plain data once per live movement tick. Its test covers all 512 relevant key combinations and records/replays snapshots through `PlayerMotion` for sprint, sneak, jump and flight rules. This is a replay of the input state machine, not player position, collisions, camera, or a complete gameplay recording.

`src/player-physics.js` now runs the live movement segment on plain coordinate objects, `PlayerMotion` and a survival state: input, water/lava, jumping, flight, ladders/webs, collision, gravity, fall tracking and finite-world handling. The browser supplies its existing vectors and continues with survival and world ticks after the movement step. Seven recorded control sequences (295 ticks) match the position, velocity, flags, motion state, exhaustion and messages captured from the pre-extraction browser code at commit `9447171`: land/wall, water/flight, lava, ladder, web, world edge and high-altitude respawn. `tools/capture-player-physics-baseline.mjs` regenerates the port traces from that pinned `main.js` and the current fixture/dependencies; review dependency changes before replacing the baseline. The trace is not original Java evidence.

`src/player-environment.js` separates the live player air, wetness, suffocation, fire and block-collision tail, plus the later movement exhaustion/landing step. It preserves synchronous hooks for weather, potion/drowning particles, fizz, trampling and landing dust; falling-block updates and display ticks still occur between its two steps. Tests exercise drowning, suffocation/cactus hurt resistance, rain/fire/web ordering, landing and Creative void damage using the real Survival class. These are port regression checks, not an integrated original-client oracle.

`src/simulation-replay.test.js` replays 180 recorded movement ticks with real Survival, falling-block, weather and block steps, checking player state, health, queues, falling entities, block edits, shared random state and ordered outputs through seven JSON checkpoints. It checkpoints both queued and airborne sand and exercises player damage, jumping, wall collision and fluid changes. Its synthetic checkpoints include transient player motion and hurt resistance and are **not** the browser save format; clear weather and no active bolts are used. The scenario does not run all of the live tick's gameplay systems.

`src/entity-simulation.js` now runs the live nonliving-entity segment: item motion, snapshot-ordered TNT ticks, living-player item pickup, thrown projectiles and their hatch/sound events, mob-event draining, then arrows and their pickup/flush. Explosion, target selection and presentation hooks still run synchronously in the caller, including TNT edits before pickup and arrow ignition after the TNT pass. Tests check callback order, dead-player pickup exclusion, newly primed TNT waiting until the next tick, and real item movement/pickup.

`src/player-item-use.js` runs the live food, milk and bow-use counters. Seven tests cover all 32 food/drink ticks, six cadence effects, final crumbs before consumption/chance rolls, milk clearing effects in Survival and Creative, cancellation on a held-item change, failed completion and bow drawing. The browser supplies synchronous particles, sounds and UI hooks, plus its existing random provider. Starting/releasing use and other input actions remain in `main.js`.

`src/entity-simulation-replay.test.js` compares 12 ticks through three JSON checkpoints using the current serialized item, projectile, arrow, TNT, inventory, block-edit and shared-world-RNG fields. `src/living-simulation.js` now runs inhabited-time tracking, mob updates, the player tick counter, XP-orb motion/pickup and level-up feedback, then mob-event draining. `drainMobEvents` is shared with immediate attack/interaction and projectile event handling: sound, death XP spawn, explosion, item drop and eat-grass feedback retain their original per-event order. Death XP spawned at the end of the living segment cannot move or be collected until a later tick; the earlier projectile/event drain still precedes the living segment. Tests cover this ordering, real XP level-up/pickup, Creative-compatible rewards and dead-player pickup exclusion. Explosion execution and grass presentation remain synchronous caller hooks.

`src/living-simulation-replay.test.js` compares 35 ticks against an independent copy of the old `main.js` ordering at `90f8807`, using real EntityWorld, ExperienceOrbs, Experience, ItemEntities and Creative Survival. The flat synthetic fixture fixes random streams and transient orb IDs. This is a port differential regression, with no save continuity or original integrated Java claim.

`src/player-mining.js` takes plain tick state for the current target/tool, held/automatic input, progress and cooldown. It preserves the playing gate, target/block/tool invalidation, same-tick mining started by the edit hook, float32 accumulation, dig/swing order, completion delay and hit particles during cooldown. The live edit hook immediately returns updated mining/cooldown fields; hit particles read the world after any instant/completed break. Ten tests cover these paths with real Survival progress. Block removal/drops and click dispatch remain caller-owned.

`src/block-break-simulation.js` now owns the live player block-removal path: guards, harvest/drop decisions, metadata, gravel/crop/leaf rolls, ice-to-water replacement, container contents, ore XP, exhaustion and tool wear. It accepts the held tool and coordinates as explicit inputs, and invokes its scene/UI/audio observers synchronously after the mutations. Ten tests cover guarded and failed removals, drop metadata and RNG, snow counts, leaf/shear behavior, ice, container spilling and Creative behavior. Existing Math.random and Trees.random streams stay separate; this extraction does not add a saved random stream or change the current drop rules.

`src/explosion-simulation.js` now owns the live explosion orchestration. It prepares ray/drop results, applies mob/nonliving/player hits and knockback against the existing blocks, emits burst/sound hooks, then removes blocks, observes farming, spills containers, spawns drops/XP and primes chained TNT before final scene/UI hooks. The broken-tool hook remains within player damage before player knockback. Two focused tests check this ordering with real ray/drop/container systems and Creative knockback without player damage. World.rand and the current Math.random use for new TNT stay unchanged.

`src/block-actions-replay.test.js` compiles the exact `breakBlock`/`explodeAt` bodies captured from `main.js` at `c1d239b` in `block-actions-port-reference.json` (source SHA-256 retained). `src/block-placement-simulation.js` owns ordinary ItemBlock, snow-stack and reed placement decisions. It accepts plain player coordinates, current inventory and a copied target, preserving support/bounds checks, metadata, temporary collision probes and rollback, chest facing, farming observation, item consumption and observer order. `src/player-edit-simulation.js` owns the live click dispatch decisions and mutable eating/mining/cooldown state. Fourteen tests cover early projectile/bow/bucket precedence, workbench/chest activation, attack critical/sprint order, entity interactions, food, hoe/TNT/fire actions, Creative/sword rules, instant-break callback arguments and placement delegation. Hooks keep their original arguments. Container-opening adapters refresh the state fields that the existing GUI code resets. Snowball/egg throws and bucket use now call the headless steps below directly; GUI execution remains a synchronous caller adapter.

`src/player-actions.js` captures one edit request as versioned JSON data with detached block/adjacent coordinates, finite distance, held item ID, an optional stable mob ID and (version 2) the held bucket's captured trace or null. Dispatch validates the request, checks/refetches the held ID from current inventory, resolves a live mob and invokes the edit helper immediately. Invalid coordinates, mismatched items and missing/dead/idless mob targets are consumed without falling back to a block action. Seven tests include JSON mutation isolation, mob-0 compatibility, stale inventory snapshots, repeated real placement, rollback, real creeper ignition and the old bow fast path compiled from stored verbatim `91fcbd4` edit source (source SHA-256 checked). Only that bow branch is a pinned-source differential; the other cases are port regressions.

Development builds expose `window.__mc.editActions`: a detached copy of the latest 256 edit and use-release calls with their player tick and captured action, cleared on world launch. Edit records include the bucket ray/hit for bucket clicks; every right-button release is recorded, whether or not a bow was drawn. This is a diagnostic trace, not a save format or full input recording: camera/inventory setup, hotbar selection, per-tick draw state, item dropping, GUI transactions, RNG and world state are not captured.

`src/buckets-simulation.js` owns live bucket use. At input time `captureBucketTarget` traces the held empty or filled bucket's own ray (the last frame's eye ray, 5 blocks, stopping on liquid sources only when empty) and stores the ray, its liquid flag and the hit block/side as JSON; a milk bucket or other item captures nothing, and a missing or NaN ray is recorded as no ray. `useHeldBucket` then runs against the current world and inventory: milk starts the 32-tick drink in either mode, a live cow takes an empty Survival bucket first, otherwise the captured ray is retraced and must reproduce the captured hit. A mismatched (stale) or malformed capture is consumed without world, inventory or hook effects and never falls back to a block action. Plant replacement calls `fluids.wash`, then the particle and sound hooks; changed cells, the equip reset (only when the held stack changed), hotbar and unsaved hooks follow in the old order. `useBucket` in `buckets.js` is split into the trace and `useBucketAt` without rule changes. Five tests cover capture/detachment, stack pickup, stale and malformed records, flower replacement, Creative lava, cow milking with a full inventory, Creative cow fallthrough and milk.

`src/player-throw-simulation.js` owns snowball/egg throws and bow release; no other thrown items (ender pearls, potions, fishing) exist in this build. A throw draws the `random.bow` pitch before the projectile's Entity.rand seed (both from `Math.random` live), spawns the ball, and in Survival takes one item and fires the equip-reset/hotbar/unsaved hooks. Release always ends the draw, then requires the playing screen and a held bow; `releaseBow` keeps power, velocity, critical, wear, arrow use and Creative pickup rules, and `flushArrows` stays the presentation hook. `captureReleaseAction`/`dispatchReleaseAction` record the release as plain data and apply it immediately. Three tests cover RNG order, Survival/Creative throws, full/partial/Creative shots and the four non-shot releases.

`src/player-throw-replay.test.js` compiles the verbatim `edit`, `useBucketItem`, `throwSnowball`, `releaseBowUse` and `flushArrows` bodies plus the `player-actions.js`/`player-edit-simulation.js` modules stored from `8901a28` in `player-throw-port-reference.json` (SHA-256 checked; verified against Git history when it is present). The other side compiles the same-named functions from the current `src/main.js` with the current modules. Every step's inventory, eating/mining/cooldown/unsaved state, blocks, projectile/arrow/item records, critical flags, ordered presentation calls and the total random draw count match. The only textual change made to compile either side is `import.meta.env.DEV` becoming a parameter. This is a port regression on a flat synthetic arena with stubbed farming/scene/audio, not native Java evidence or a save/reload check. These changes do not establish whole-game, native Java, save or networking readiness.

These are segments of the existing tick, not a complete authoritative simulation. Item dropping, hotbar selection, GUI/inventory transactions, mouse-look/eye-ray capture itself, full state/save ownership and presentation remain interleaved in `main.js`; falling blocks are still invoked there. Farming uses the supplied scene daylight. Fluid/fire callbacks can still produce presentation effects, and observers run synchronously, so callers must preserve their ordering and behavior. Separate per-system queues are not a native unified scheduler. Further work must move state ownership and effects across explicit interfaces, record/replay actual player actions and whole-world state, and compare whole ticks and browser reloads before claiming headless or multiplayer readiness.

## Vehicle actions

`vehicle-simulation.js` captures `player-vehicle` version-1 mount/use/attack and dismount requests (cart ID, click, sneak state, held item ID) as detached JSON and dispatches immediately against live carts/inventory. Missing/dead carts and mismatched held items are consumed. `player-actions.js` routes captured edit targets on rails to ItemMinecart placement; coordinates remain copied data. `moveRidingPlayer` skips ordinary player movement, supplies forward input, and captures sneak dismount through the same synchronous dispatcher. Cart ticks exclude their own rider's box/push, then `finishVehicleTick` attaches the player to the updated seat. Health/environment/use and other systems continue. Cart type/rider markers survive browser saves/import; only the first valid empty-cart rider restores. See [minecarts](minecarts.md) for exact native scope, finite-edge adaptation and remaining gaps. This adds native component replays and port integration tests, not complete authoritative tick/save or multiplayer acceptance. Development localhost `?silent` prevents AudioContext creation/playback for that tab without changing saved sound options.
