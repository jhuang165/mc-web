# Light engine audit (batch 20)

Compares how the port computes sky and block light with the unchanged 1.7.10 `World.updateLightByType` / `computeLightValue` and the Chunk light code. Opacity and emission per block were already probed (`block-light-reference.json`); this covers the propagation. Evidence: `tools/probes/LightEngineProbe.java`, driver `tools/verify-light-engine.mjs`, `light-engine-reference.json`, replayed by `src/light-engine.test.js`.

## Port light code

- `src/lighting.js` `LightVolume`: a 128 x 128 x height volume of sky and block nibbles (`Uint8Array`) plus a `heights` map (`y + 1` of the topmost cell with light opacity > 0, like `Chunk.heightMap`; 256 in a no-sky world). `column(x, z)` recomputes one height; `relight(x0, x1, z0, z1)` solves the whole box as a bucketed flood fill: sky 15 at and above the height map, block light from emitters, each cell `max(neighbour) - max(1, opacity)` (opacity 255 blocks, an emitter that is also opaque costs 1). Light entering from outside the box is read from the cells next to it; outside the volume reads as open sky (0 with no sky). `update(x, y, z)` = `column` + `relight` of the +-15 box.
- `src/streaming-light.js` `StreamingLight`: the same solver over the resident chunk square; `shift()` slides the window and relights only the new strips.
- `src/scene.js` `applyChanges` (the `light.column` / `light.relight` block): per changed cell, skips when opacity and emission are unchanged, otherwise recomputes the column height and relights the +-15 box; overlapping boxes merge; the changed box drives mesh rebuilds. `resetLight` builds the volume (`world.streaming` picks `StreamingLight`); powered repeaters emit 9 and lit furnaces 13 through the emission callback.
- Consumers: `skyAt`, `blockAt`, `packed` (`getLightBrightnessForSkyBlocks`, with `useNeighborBrightness`), `level` (`getBlockLightValue`, mob spawning), smooth lighting/AO in `smoothFace`.

## What was probed (executed natively) and bytecode-read

Probed: the unchanged `World` (`ahb`) over a provider of real `Chunk` (`apx`) objects with `ExtendedBlockStorage` sections, chunks -2..2 (80 x 80 blocks). `World.setBlock` runs `Chunk.func_150807_a` (relightBlock / propagateSkylightOcclusion / generateSkylightMap inside) then `World.updateAllLightTypes` -> `updateLightByType`. Fresh chunks go through `Chunk.generateSkylightMap`; "settled" sets `isTerrainPopulated` and ticks `Chunk.func_150804_b(false)` (recheckGaps, `func_150809_p` checkLight of the gaps) with isRemote false. After every edit one such chunk tick runs, as `WorldServer` does each tick. 18 scenarios, 1,000+ snapshots of sha256 digests of the whole 48 x 48 x 256 interior (sky, block, heightMap) plus nibble regions. `World` is allocated without its constructor and isRemote is true during `setBlock`, so block add/break callbacks (drops, fluid ticks) do not run; the light code does not use them.

Bytecode-read: the method structure of `func_150804_b`, `func_150809_p`, `func_150811_f`, the `recheckGaps` isRemote early return, and the `updateLightByType` queue (17-block distance test, `doChunksNearChunkExist`, removal pass that only clears neighbours equal to the removed value minus opacity).

Scenarios: torch, emitters (glowstone, lava, adjacent pairs), cave torch, 1-wide shaft dug 16 deep and re-covered, 9 x 9 roof placed block by block with holes, water/leaves/ice/glass columns (opacity 3/1/3/0), a sunken water basin, a sealed tunnel opened under an overhang, a chunk border at x = 16 (torches, glowstone, roof, shaft, lava), the loaded-area edge, a Nether volume, three fresh terrains, and three seeded 220-edit random stress runs (stone, planks, water, leaves, glass, torch, glowstone, lava, ice, dirt, air).

## Result

The port's fixed point equals the native light after every edit once the chunk tick has run: all sky, block and heightMap digests match in 12 scenarios and 660 stress edits, and the settled state of flat ground equals it (and so does a fresh `generateSkylightMap` of flat ground). No port bug was found, so `lighting.js` is unchanged.

## Documented differences (each pinned by a test)

1. **Transient and stale native light.** Natively an edit leaves cells wrong until the next chunk tick (`recheckGaps` / propagateSkylightOcclusion), and a floating opaque block set into a section that does not exist yet (no block above the highest section of that chunk) runs `generateSkylightMap` instead of `relightBlock`, which leaves the cells under it at their old sky light (15) while the port gives 14 (`null-section`, step 0; the next edit of those cells makes native agree). The port is always at the fixed point at once.
2. **Fresh chunks are lit eagerly.** Natively `generateSkylightMap` only lights columns vertically (15 above the height map, then -1 per cell, minus opacity, below it) and leaves block emitters unlit; lateral skylight under overhangs, trees and cliffs and emitter light appear only when the chunk is populated, ticked or a neighbour changes, so native terrain keeps dark pockets (terrain scenarios: 44-80 differing cells in a 17 x 17 x 25 region, all darker natively). The port propagates everything when the volume is built or a column streams in. Heights agree.
3. **Unloaded neighbours.** `updateLightByType` returns without doing anything when any chunk within 17 blocks is not loaded (`loaded-edge`: a torch 20 blocks from the loaded edge has no effect natively). The port has no unloaded chunks inside the resident square, so the same edit lights.
4. **No-sky worlds keep height 256** in `heights` (the native heightMap holds the real top); block light matches exactly in the Nether scenario.
5. **Timing.** The port relights the whole +-15 box synchronously; natively the incremental queue is bounded (32,768 entries, 17-block Manhattan distance) and spread over `setBlock` and the chunk tick.

Not covered: End/Nether worlds with real generated terrain, and lighting across the 128-block volume edge and `StreamingLight.shift` (covered by `streaming-light.test.js`). Batch 25 (below) covers `func_150809_p` ordering, the queue limits and overflow.

## Batch 25: native incremental engine (`src/native-light.js`)

`NativeLight` is a line-by-line port of `World.updateLightByType`, which has a 32,768-entry `Int32Array` queue. Its removal pass checks `j < length`. Its addition pass checks `j < length - 6` and the 17-block Manhattan reach. Every neighbour push from the removal pass that is dropped is counted in `stats.overflow`. The port also covers `checkChunksExist` / `doChunksNearChunkExist(17)` and the Chunk light code with its null-section rules (`generateSkylightMap`, `relightBlock`, `recheckGaps`, `func_150804_b`, `func_150809_p` in its bytecode neighbour and edge order, `enqueueRelightChecks` with the 4096-check counter, and `populateChunk`'s isTerrainPopulated/isLightPopulated sequence). Evidence: `tools/probes/LightEngine2Probe.java`, `tools/verify-light-engine2.mjs`, `light-engine2-reference.json` (9 scenarios, 170 snapshots). `src/native-light.test.js` replays these and the 18 batch-20 scenarios; all 27 match exactly.

- The 32,768 queue never overflowed naturally (the peak was about 29k in a cavern stress run). The overflow path is verified with 4096- and 1024-entry queues, which change the light in 21 of 41 snapshots. A reach of 30 instead of 17 changes 5 of 41.
- `unloaded-edge`: a torch within 17 blocks of an unloaded chunk is skipped while that chunk is unloaded; the snapshots after the cx = 1 column loads are matched too.
- `fresh-spiral-301/302`, `fresh-xmajor-301`: fresh chunks are loaded in a spiral or x-major order with server populate (decorations, trees, torches, lava). The test replays the probe's `HashMap<Long>` iteration order (`hashMapOrder`); tick order made no difference in the scenarios.
- `null-sections`: a floating block above the top section leaves stale sky 15 under it. A later block below the height map creates a section with zero sky across the whole chunk, including open air. Server ticks keep it dark. After `reset` (`Chunk.n`), `enqueueRelightChecks` heals part of it by 32 ticks and all of it by 512.
- Bytecode-read only: server chunks start with the counter at 4096, so `o()` does nothing. The client resets it on chunk receive, `WorldClient.func_147456_g` checks at most 10 chunks per tick, and `func_150804_b` runs with isRemote true (one-column recheckGaps).

Batch 25 left it test-only. Batch 26 wires it in (next section).

## Batch 26: native light in the Overworld (`StreamingLight`, default on)

Streamed Overworld worlds (`world.streaming`, not the Nether/End) now run edits, gap rechecks and window shifts through `NativeLight`. `?nativeLight=0` (or localStorage `blockworld.nativeLight` = `0`) switches back to the fixed-point path; `NATIVE_LIGHT_DEFAULT` in `src/streaming-light.js` is the default.

- The first sky/block arrays still come from the eager `LightVolume` build; `NativeLight` shares those arrays. Per chunk it adds the section mask (sections holding a non-air block; the light arrays of a missing section are rewritten to its rule: sky 15 at or above the height map, 0 below, block 0), `hmMin`, no pending gaps, `isLightPopulated`, and the 4096 relight counter. At the default spawn this changes no light cell against the fixed-point build.
- `scene.updateBlock` and `scene.updateBlocks` call `World.setBlock`'s light half through `StreamingLight.update(x, y, z, oldId)`: the replaced block's opacity comes from the caller (fluids, explosions) or from an id shadow kept by the light volume. Edits do not relight a 31 x 31 box any more; they follow the 17-block queue.
- `scene.setTime` (once per game tick) calls `StreamingLight.tick()`: `Chunk.func_150804_b` for every resident chunk with pending gaps. Changed cells are remeshed with the usual dirty queue.
- `shift()` translates the per-chunk arrays and the id shadow with the light arrays; chunks entering the square are initialised after their strip is relit.
- The outer ring of the 8 x 8 chunk square counts as unloaded: an edit within 17 blocks of it is skipped (the middle 4 x 4 chunks always light, plus the parts of the next ring that stay 17 blocks from the edge), and the ring reads the unloaded defaults (sky 15, block 0).
- Differences now visible in play (all 1.7.10 behaviour, replayed by `native-light.test.js`): a first block placed in an empty section leaves the cells under it unlit or stale; edits near the square's edge keep stale light; a light update never reaches past 17 blocks.
- Still not native: relight checks run only for chunks reset by `resetRelightChecks` (none here), chunk population ordering does not run (the eager build fills the arrays), and the client-side scheduling is bytecode-read only.
- `src/streaming-light-native.test.js` (8 tests): the switch, initial state, edits equal to the fixed-point volume where native agrees, the dark-pit difference, the edge skip, shifts equal to a fresh build along each axis and after long jumps, and the deferred build.
- Timings (muted headless Chrome, 3 runs each, `artifacts/b26-lighting3/measure.mjs`, machine shared with other tracks): new world playable 1.02-1.53 s with the old path, 0.92-1.33 s native; longest long task after load 0-136 ms old, 0-99 ms native; one-chunk shifts 63-94 ms old, 58-124 ms native; a 20-edit loop averages 11-15 ms per edit old and 8-26 ms native. The two paths are within noise of each other; the load itself has a 90 ms long task in both.

## Batch 27: ring edits, the block tap, the Nether and End (`light-engine3-reference.json`)

New native evidence: `tools/probes/LightEngine3Probe.java` (`node tools/verify-light-engine3.mjs`) runs the unchanged `World`/`Chunk` light code over chunks -3..3 (digests x, z -48..63) with the real `WorldProviderSurface` (`aqq`), `WorldProviderHell` (`aqp`) and `WorldProviderEnd` (`aqr`), each registered through its own `registerWorldChunkManager` (`b()`). 9 scenarios (all-loaded edits on the outer chunks, the opposite side, placements only, plugged cavern holes, Nether and End with and without lava, and 64 distinct edits in one chunk followed by relight checks) replay in `src/native-light-ring.test.js` and match the unchanged classes at every snapshot.

- Flags: `aqo.g` is hasNoSky (Nether and End, bytecode and probe), `aqo.f` is isHellWorld (Nether only). `World.getActualHeight` is 128 for both, 256 for the Overworld. `lightBrightnessTable` (`aqo.h` after `generateLightBrightnessTable`) is the float table `dimensions.js` computes; the probe showed `lightBrightnessTable(0.1)` was one ulp off at entries 5 and 6 because 0.1 is a float field (fixed: `ambient = fround(ambient)`).
- Sky in a no-sky world is not all zero. A missing section above the column's heightMap reads sky 15 (`Chunk.getSavedLightValue`: `canSeeSky ? 15 : 0`), existing sections read 0, and creating a section by a light write zeroes its sky nibble. The earlier assumption (`World.getSavedLightValue` answers 0 before looking at the chunk) was wrong; `NativeLight.saved` and `syncColumn` follow the probe now. The Nether heightMap is the real top solid block (probe: 41 over a 40-high floor, 128 above a ceiling).
- Ring facts: natively an edit's light is refused when any chunk within 17 blocks is missing, so with the 7 x 7 square only x -31..46 lights. Edits outside it change blocks and heights only.
- Ring edits (not native, a port model, `replaySkipped`): a refused update records its centre cell; an edit into a non-resident chunk records the setBlock; both are translated with the window (`shiftDeferred`) and replayed when the neighbourhood is resident (`replayDeferred` after `shift`, and after a column is initialised). Exact against the all-loaded native result for placements, the cavern hole plug and reopen, the opposite ring, and Nether/End block light and heights. Not exact: place-and-remove pairs of a roof over a hole (about 5.5k sky cells differ, block light exact), because the removal passes the refused update never ran leave a different intermediate state; emitters are respread (`spreadBlock`) because an update that reached an emitter whose own update is queued would otherwise cut its spread at the first reach. The Nether and End sky nibble of sections no light write created stays 15 where native may have zeroed it (above ceilings).
- `StreamingLight` now uses the native engine in the Nether and End (`world.lightNoSky`), `?nativeLight=0` still returns to the fixed-point volume. `world.blockTap` (set by `put`) notes every changed cell, so `world.set` with no `updateBlock` still lights and the id shadow follows; `tick()` processes them with the other edits. A chunk with 64 distinct changed cells in a tick runs `resetRelightChecks` (the `PlayerInstance` resend, bytecode-read in `mr`; the client then runs `enqueueRelightChecks` 8 cells per tick). Ring columns journalled with `rememberEdit` are in `world.get` and in the light once the window reaches them (test).
- Cost (node, same machine, before/after the batch): torch place plus remove with ticks 0.93 -> 1.08 ms, shift 164 -> 164 ms, 2000 `world.set` calls 0.13 -> 0.11 ms (the tap is one null check plus a branch when no volume is attached). Muted headless Chrome (`artifacts/b27-lighting4/check.mjs`): a torch at the window edge reads 0 and records 4 refused updates, then 14/13 after the window moves 48 blocks; a tapped `world.set` reads 14; Nether and End torches read 14/13 with sky 0 in the built section and 15 above the missing sections.

## Batch 29: ring column light, and server light against client relight

- **Ring columns (`src/ring-light.js`, `RingLight` in `headless-columns.js`).** A held ring column used to answer light with a per-cell reverse search (about 30k grid cells reset per query). A column asked about 6 times by the search is now lit whole: the 3 x 3 chunks around it are read into a work volume, sky is seeded where the height map is above a neighbour (and the cell above every column's top, which may be translucent), block light at every emitter, and both spread by value with the rule of `World.computeLightValue` (brightest neighbour minus max(1, opacity), opaque cells receive nothing, an opaque emitter costs 1). That is the fixed point `LightVolume` keeps for the resident window and the one a column holds when it becomes resident (the eager build under `NativeLight`), so the values do not change when the window reaches the column; only the edit-history effects of the native engine (queue bound, 17-block skip) are not modelled, as before. A column is lit only when its eight neighbours are resident or held (otherwise rim columns would be lit against air and recomputed), at most two per tick, and the result is dropped for the column and its eight neighbours on any edit, arrival, adoption, hydration, prune and window move. Typical cost 0.6 to 1.4 ms a column (node, warm). Height maps (`col` height per cell) and precipitation heights are cached per column too (`HeadlessColumns.state`, rebuilt when the column's stamp moves); `weather.js` `precipitationHeight` and `canSeeSky` read them for held columns (two guarded lines), and `canLightningStrikeAt` returns false before any column read when it is not raining (the first test of `ahb.y`).
- **Equality (`src/ring-light.test.js`, 3 tests).** Bulk light against `StreamingLight` over three columns, 115,200 cells, fresh and after a roof, torch, glowstone and a hole were written through `putOutside` (invalidation is required for the second pass: dropping it fails the test). Night spawning (200 ticks, time 18000, seven ring chunks with stone roofs, leaf canopies and torches) is identical with bulk light, with the per-cell search and with every chunk resident, including the spawns that stand under cover. Cold rain over ten ring chunks, 1,800 ticks, a pond half roofed, a torch beside it and a second torch at tick 900: the generator states and the final blocks (ice and snow counts) equal the all-resident world with the uncached search as reference. Earlier equality tests compared two `RingLight` instances over the same blocks; these compare against the volume or the uncached fixed point.
- **Server light against client relight (bytecode-read, `javap` of `bjb` NetHandlerPlayClient, `bjf` WorldClient, `apx` Chunk, `ahb` World, `mt` WorldServer; not executed).** The integrated client holds its own chunks, separate from the server's:
  1. Chunk receipt (`bjb.a(gx)`): `Chunk.fillChunk` copies the block data and the light arrays the server sent (sky included unless `hasNoSky`), then `resetRelightChecks` (`apx.n`) only when the packet is not a full chunk or the provider is not `WorldProviderSurface` (`aqq`). An Overworld chunk keeps the server's light; Nether, End and 64-change resends re-check it.
  2. A block change packet runs `WorldClient.func_147492_c` (`bjf.c`) -> `ahb.d(x,y,z,block,meta,3)`, the same setBlock as the server: `Chunk.func_150807_a` (relightBlock, propagateSkylightOcclusion) then `World.t` (`func_147451_t`, updateAllLightTypes) with no `isRemote` guard. The client's own `updateLightByType` therefore runs over the client's loaded chunks (17-block skip at the client's edge).
  3. `Chunk.func_150804_b` (`apx.b(Z)`, the per-tick recheckGaps and light-population work) is called only from `mt` (WorldServer); neither `bjf` nor `bjd` calls it. The client never runs `recheckGaps` (so neighbour-column sky fixups of a changed height map are not done there, although `recheckGaps` has an `isRemote` branch) and never light-populates a chunk. `bjf.g` (`func_147456_g`) calls `func_147467_a` once per newly active chunk, ten a tick, which ends in `apx.o` (enqueueRelightChecks).
  4. The server sends no light-only changes, so a server-side light change without a block packet (a refused flag-0/1 write, population spilling into a sent chunk when no block changes) is not seen by the client until the chunk is resent.
- **What would be visible (predicted from the bytecode, not executed).** After an edit that changes a column's height map, the client lacks the server's tick-later `recheckGaps` pass over the neighbouring columns, so sky light in the cells between the old and new heights beside a freshly opened shaft or roof can differ (the server relights them, the client keeps what `relightBlock` and the one `updateLightByType` of the edited cell left). Spawning, lightning, mob AI and ice read the server light, rendering reads the client light. The port has one volume, running the server model (it ticks `recheckGaps`), so rendered light beside such edits can be brighter or darker than native 1.7.10's. Not ported: it needs a second `NativeLight` (two 8 MB light arrays, a second set of edits and no tick work) fed by the same block changes and chunk loads, and a probe over the unchanged `ahb`/`apx` classes to confirm the size of the difference before anyone relies on it.
- **Cost of the ring reads (muted headless Chrome, End to Overworld, `artifacts/b29-ringlight/`).** See `.shared-memory/notes/ringlight-b29-track.md` for the before and after returns.

## Batch 30: ring rim, resident edits beside ring columns, server against client light

- **Rim columns (model, `ring-light.js`, `RingLight` in `headless-columns.js`).** A held column with a neighbouring chunk that is neither resident nor held used to be lit with the missing chunk read as open air (sky 15 flowing in under overhangs), brighter than native. Natively `updateLightByType` does nothing within 17 blocks of an unloaded chunk and generation leaves lateral light lazy, so nothing is lit from or across an unloaded chunk. Closest bounded model: a missing neighbour chunk is a barrier (no sky seeds, no emitters, receives and carries nothing), in both the bulk light (`computeColumnLight`) and the per-cell search (`present` mask of the 3 x 3 chunks round the query). Rim columns are now lit by the bulk path like any other (the `complete` gate is gone); a light is dropped when a neighbour arrives (`store` -> `invalidateLight`). The result is never brighter than the fixed point and is darker than native's lazy vertical-only rim light only by whatever lateral light native would have had from earlier updates. Not native-exact: native rim chunks hold `generateSkylightMap` light (vertical only) with unspread emitters, which is darker still. Test: `ring-light-rim.test.js` (a roofed rim column reads 0 under the roof against 14 before; an interior one still lights from its held neighbour; bulk and search agree).
- **Resident edits beside ring columns.** `World.put` calls `ringSink.edited(x, z)` (one guarded line in `world.js`). `HeadlessColumns.edited` drops the bulk light and `asked` count of held non-resident columns in the eight chunks round the edit (light reaches 14 cells, so no farther) and clears the search cache only then; an edit with no held neighbour costs nine map lookups. Before, such a column kept stale light until the window moved. Test (fails without the hook): a torch placed and removed in the last resident column reads 13 and 0 in the ring column beside it, bulk and search.
- **Server light against client relight (executed).** `tools/probes/LightClientServerProbe.java` (`node tools/verify-light-client-server.mjs`, `light-client-server.jsonl`, replayed as facts by `light-client-server.test.js`) runs the unchanged `World`/`Chunk` classes twice over chunks -3..3. The server world settles, then runs `o()` and `func_150804_b(false)` on every chunk each tick. The client world copies the server's blocks and sky/block light arrays chunk by chunk (as `fillChunk`), skipping empty sections (S21PacketChunkData omits `isEmpty` storages), runs `generateHeightMap`, and never calls `func_150804_b`. Both run the same `setBlock` flag-2 edits; two client variants (no tick work, and `o()` every tick). 8 records (4 edit scripts x 2 variants), about 100 edits: pillars and pits on flat ground, a nine-block floating slab built and removed, cavern roof shafts and plugs with glowstone, hillside ledges and a tower.
  - Block light and height maps never differ. Sky light differs in two ways. (1) Right after the chunk packet, 288 to 512 cells in empty sections 4 and 5 (y 64..95) beside the shadow of pillars are 0..14 darker on the client, because the packet carries no empty sections (the client reads 0 below a height map there). Only a fully empty section under another column's top can show this; ordinary terrain rarely has one. (2) The first block of a floating slab (`0,70,0`) leaves 9 cells below it differing in the same column (server 14, client 15 at y 61..63 and 0 at y 64..70): the documented null-section case, where the server's `recheckGaps` repairs what the client keeps. No other edit in the scripts, including height-map changing pillars, pits, shafts, roof holes and cliff digs, produced any difference beyond (1). Without `recheckGaps` the client did not diverge there.
  - Decision: not ported. The measured rendered-light difference is nine cells in one rare edit, and an empty-section start effect, so a second `NativeLight` (two 8 MB arrays and a second edit stream) would buy nothing visible. Spawning, growth and ice keep reading the one volume. Limits: chunk packets are modelled as a copy (population spill into already sent chunks, 64-change resends and the Nether/End `resetRelightChecks` path are not in this probe), only the Overworld provider, and the sets run with `isRemote` true as in the other probes.

## Batch 31: the rim of the loaded set (`rim-light-reference.json`), and the 64-change resend

- **Native evidence (executed).** `tools/probes/RimLightProbe.java` (`MC_RESEARCH=<dir> node tools/verify-rim-light.mjs`, `rim-light-reference.json`) runs the unchanged `World`/`Chunk` light code with the `LightEngine2Probe` provider (`ChunkProviderServer.populate`, then the decoration blocks through `World.setBlock` flag 2, one server tick after every load) over terrain on chunks -7..7: 4-block stone/dirt/grass columns (some under water), caves, floating slabs, 260 trees, torches, glowstone. The loaded set grows 9 x 9, 13 x 13, 15 x 15, in spiral and x-major order, seeds 311 and 312; a fifth record is a Nether (`WorldProviderHell`, `aqp.b()`, `resetRelightChecks` on every generated chunk as `ChunkProviderHell` does) with a lava sea and glowstone, plus 600 more ticks. Each snapshot is a per-chunk digest of sky, block light and height map for all 225 chunks. `NativeLight` replays all five records exactly (`rim-light.test.js`; 5 x 3-4 snapshots x 225 chunks), so the replay is the reference for the numbers below.
- **What the outermost loaded chunks hold (`depth 0` = the ring of chunks with an unloaded neighbour).** Compared with the model of batches 29/30 (a fixed point where the missing chunks are barriers) the native rim chunk differs in 66 to 164 sky cells and 13 to 240 block cells per chunk. Compared with `Chunk.generateSkylightMap` of the final blocks (sky straight down each column, no lateral light, sections that exist only) and no block light, it differs in 4 to 29 sky and 2 to 24 block cells per chunk (all seeds, orders and sizes). The mechanism is the one batch 20 documented: generation lights only vertically, terrain emitters are never spread, and `updateLightByType` refuses (`doChunksNearChunkExist`, 17 blocks) every update beside an unloaded chunk, which includes the population of the outermost chunks and the setBlocks of their spilled decorations. The rule holds on both sides of the set: the +x/+z edge chunks are not populated yet, the -x/-z ones are, and both read the same.
- **Port (`ring-light.js`, `headless-columns.js`).** `isRim(ring, cx, cz)`: a held, non-resident column with a neighbouring chunk (of eight) that is neither held nor resident. A rim column's light is `verticalLight(col)` (the rule of `generateSkylightMap` above, plus the 15-above-height-map of a missing section), block light 0, answered at once (no per-tick budget, no hot count). Its emitters are also off in the bulk light and the per-cell search of the columns beside it (`emits` mask); its sky still flows in. `invalidateLight` now covers 5 x 5 chunks, because a column's rim state and the emitters of its rim neighbours depend on what is held two chunks away. Nether and End use the same rule (sky stays 0). `ring.noRim` restores the batch 29/30 barrier model (test hook).
- **Result on the records.** Overworld, per rim chunk: sky 132/139/66/164/73/87 cells (barrier model) to 16/14/4/12/29/9, block 175/13/194/218/237/148 to 13/17/10/24/3/2 (seed 311 spiral, 312 spiral, three sizes each; the other orders are in the test). Nether: block 7,650 to 7,990 cells per rim chunk to 36 to 195 (sky is 0 there; the harness ignores it).
- **Not modelled (measured).** The second ring in and deeper are not a function of position: whether an emitter or lateral light there exists depends on whether its population ran while every chunk within 17 blocks was loaded, i.e. on load order. The model stays at the fixed point there. Native block light is darker than it by 100 to 640 cells per chunk at depths 1 to 3 in every Overworld record, and stays so after more neighbours load (a stale emitter is only repaired by a later update beside it); sky is within 14 to 56 cells per chunk. In the Nether, with the relight counters of the generated chunks reset, even depth 3 and the chunks 600 ticks after loading differ from the fixed point by 6,700 to 8,400 block cells per chunk (`enqueueRelightChecks` 8 slots a tick per chunk, the lava sea is terrain). The window's eager build (documented difference 2 above) has the same property: the port lights what native would leave dark. Both are batch 20's "not replicated on purpose" list, unchanged.
- **64-change resend (executed, `light-client-server.jsonl`, case `resend64`).** `PlayerInstance` sends a chunk with 64 changed cells as a partial chunk packet (flagged sections), not as block changes (bytecode-read in `mr`). The probe runs 70 edits in chunk (0, 0) (stone, glowstone beside the chunk edge, a slab at y 70) on the server, copies the flagged sections' blocks, metadata, sky and block light to a client that did not run those setBlocks, then `generateHeightMap` and `resetRelightChecks` (partial packet). Result: 3,983 block-light cells in the unflagged chunk -1 (x -14..-1, max 14) stay 0 on the client where the server has the glowstone light; client ticks do nothing; 600 ticks of `Chunk.o()` (8 cells a tick; the client only runs it for newly active chunks, so this is an upper bound) heal 255. The client is never brighter, heights never differ. The port has one volume running the server model, so it renders the lit cells; not ported (it needs the second light volume of batch 30 and only shows in the neighbour chunk of a 64-change batch, e.g. a big explosion at a chunk border).
- **Population spill** into chunks already sent is not added to the client probe: population writes go through `setBlock` flag 2, which sends block changes (or the resend above), so the client's own `updateLightByType` runs for them; the remaining difference is the load order dependence measured above.
