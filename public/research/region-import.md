# Import a Java 1.7.10 region area (WORLD-03g)

`src/region-import.js` converts up to 8×8 chunks (128×128 blocks, Y 0–255) from one or more 1.7.10 `.mca` files into a new Blockworld export. The existing **Import** screen accepts it unchanged. It extends the single-chunk [terrain preview](chunk-preview.md) and composes [region containers](region-file.md), [chunk NBT](chunk-nbt.md) and the block registry. It is a one-way conversion. It does not open a Java world in place or write anything back, and it is not full save migration.

```sh
# Generator area of the source seed (recommended): surrounding and untouched terrain match.
node tools/import-java-region.mjs --seed -4172144997902289642 --out spawn.blockworld.json world/region/r.-1.0.mca world/region/r.-1.1.mca
# Any area of up to 8x8 chunks, north-west corner at chunk (-3, 30):
node tools/import-java-region.mjs --area -3,30,4,4 --out base.blockworld.json world/region/r.-1.0.mca
```

A whole save (`--save World`, or `--level level.dat`) imports level.dat, the player and stats/<uuid>.json and continues the world with its own seed, WorldType and generator options: see [level-dat](level-dat.md).

Options: `--landscape java|javaAmplified|javaLargeBiomes` (match level.dat `generatorName`), `--destination cx,cz`, `--missing generated|air`, `--survival`, `--name`, `--no-sky`, and `--report report.json`. Inputs open read-only, are capped at 64 MiB each, and must have canonical `r.<x>.<z>.mca` names. Outputs must be new files. The JSON report goes to stdout. A rejected conversion still prints its report when one exists.

## How the export is built

The browser has no Java save loader. An imported version-9 Java world is its seed's generated 128×128 area plus a list of per-cell `edits` (`World.restore`). The converter generates the base world for `--seed`, maps every source cell through `fromOriginal`, and records only the cells that differ.

- **Placement.** Source chunk `(area.chunkX + i, area.chunkZ + j)` becomes live chunk `(destination.chunkX + i, destination.chunkZ + j)`. Local cell offsets and Y are kept. Region, slot and embedded `xPos`/`zPos` are all checked. Negative chunks use Java signed shifts. Tile entities and dropped items move by the same block offset. The default destination is the generator position when the area lies inside the base world's generated chunks; otherwise the area is centred.
- **Edit budget.** `World.restore` accepts 100,000 edits, and the Import screen accepts files of at most 8 MiB. When the base seed is the source world's seed and the area is its generator area, only player edits and population need edits: ores, trees and structures. Terrain shape, caves and ravines regenerate identically. An unrelated base seed differs at nearly every surface and cave cell. With an unrelated seed, expect only a few chunks to fit; check the report's `edits`. A full 8×8 area does not fit. Over-budget conversions fail and report the edit count. They are never truncated.
- **Missing chunks** (an empty slot or a region file that was not supplied) are listed with the reason. `generated` (default) keeps the base world's terrain there. `air` clears the full column to void, which costs edits.
- **Light** is not carried. The browser recomputes sky and block light from cells on launch, as it does for every import. Source `SkyLight`/`BlockLight` arrays are only validated.
- **Biomes** are not carried: the export format has no biome field, and the generator supplies biomes. The report compares source `Biomes` bytes with the base world's: `compared`, `matching`, `differing`, `unset` (255).

## Contents

- **Blocks** use `fromOriginal`. Unsupported states become air; the report lists them by `id:meta` as `unmapped` (registered) or `unregistered` (unknown, including Add-nibble high IDs). Approximations list the browser target and any runtime state the export cannot hold: fluid `flowing`, farmland `moisture`, furnace `facing`/`lit`. Chest facing is not counted as an approximation because each chest cell gets a chest record with its facing.
- **Chests** (`Chest` tile entities on a chest cell) carry 27 slots (`Slot & 255`, like TileEntityChest). **Furnaces** carry three slots (signed Slot), `BurnTime` and `CookTime`. The fuel's burn time is recomputed, matching TileEntityFurnace.readFromNBT. These records go in `player.chests`/`player.furnaces`, which `legacyPlayer` and `Survival` already load. Omitting `player.slots` keeps the default Creative hotbar.
- **Items** map through the same original-ID table as the item catalogue (`tools/inventory-replay.mjs` `MC_IDS`, checked equal in the tests). Durability is kept (clamped to the maximum). Wool, flower and dye damage are kept as variants. Other non-zero damage values are unsupported. Item NBT tags (enchantments, names) are stripped and counted. Counts above the browser stack limit are clamped. Non-positive counts and unmapped items are lost by `id:damage`.
- **Entities**: dropped items (`Item`) convert to saved drops. Pos, Motion, Age (≤5,999) and PickupDelay (≤40, the browser cap) are kept, up to the 512-drop load limit.
- **Mobs** convert to saved EntityWorld mobs (`java-mobs.js` `importedMobType`, up to 256):
  - `JAVA_MOBS` ids use their own readers: Villager, VillagerGolem, Zombie, Slime, LavaSlime, Enderman, Squid, Bat, PigZombie, Ozelot, EntityHorse, Blaze, Ghast, WitherBoss, Skeleton, EnderDragon and EnderCrystal.
  - `JAVA_SUMMON_MOBS` ids use the `/summon` reader: Pig, Cow, MushroomCow, Sheep, Chicken, Wolf, Spider, CaveSpider, Creeper, Witch, Silverfish and SnowMan. EntityList.createEntityFromNBT is the same call for chunks and `/summon`.
  - Their layouts and read-back come from [mob-nbt-reference.json](mob-nbt-reference.json) (MobNbtProbe, 22 records). HealF is clamped to the saved `generic.maxHealth`, because EntityLivingBase reads Attributes first. A tamed wolf whose Attributes still say 8 therefore loads with 8 health. The sheep fleece is `Color & 15`. Fire is kept, and so are CustomName and PersistenceRequired.
  - Creeper `Fuse` (short) and `ExplosionRadius` (byte) are kept as the mob's `maxFuse` and `explosionRadius`, which the live creeper uses for its fuse, flash, fall and explosion size (powered doubles the radius). The chicken-jockey flag has no browser state and is dropped.
- **In-flight projectiles** (`java-projectiles.js`) convert to the browser's saved projectile lists: `Snowball` and `ThrownEnderpearl` (`projectiles`), `ThrownPotion` and `ThrownExpBottle` (`thrownPotions`) and `Arrow` (`arrows`), with Pos, Motion and Rotation, a potion's `Potion` stack (or the legacy `potionValue`), and an arrow's tile, `inTile`/`inData`, `shake`, `inGround`, `pickup`, `damage`, `life` and `Fire`. A named `ownerName` becomes the local player. An ender pearl with no owner, a potion that is not item 373, projectiles outside the area or past the list limit, and fireballs (the browser saves none) are counted as lost, with the reason in the id. Layouts: [projectile-nbt.md](projectile-nbt.md).
- **Paintings and item frames** become `hanging` records and **minecarts of every type** become `minecarts` records (since batch 13; [level-dat](level-dat.md)).
- **Boats and mounts**: `Boat` entities become `boats` records. A `Riding` chain whose mounts are mobs, boats or minecarts keeps the pairs: mobs link by id and a vehicle at the end of the chain is named by the rider's `riding` (`boat-<id>`, `cart-<id>`); nothing rides beyond a vehicle (native chains never do). Verified on native chains in [riding-nbt-reference.json](riding-nbt-reference.json).
- Other entities and entities outside the area are counted as lost by ID.
- **Other tile entities** (signs, spawners, chests without a chest cell, entries outside their chunk) and **scheduled ticks** (`TileTicks`) are counted as lost.

The default mode is Creative. The start position is above the area's centre column.

## Evidence

`src/region-import.test.js` writes regions with the JS NBT/region writers, then re-imports every export through the Import screen's acceptance path: the envelope checks, `World.restore`, `importedRuntime`, `Survival` and `ItemEntities.load`. Cases:

- a 2×2 area across four negative/positive regions, with a missing region and an unused region;
- chest, furnace and item-entity conversion, plus mob conversion and lost signs, riders, bad slots, tags and an off-chunk tile;
- unmapped, unregistered high-ID and approximated states;
- a full 8×8 generator area rebuilt from its own seed in exactly two edits, with all 16,384 biome bytes matching; the same chunks under a misaligned base exceed the budget;
- three original AnvilChunkLoader payloads from [chunk-nbt-reference.json](chunk-nbt-reference.json), whose cell inventory equals [region inspection](region-inspection.md);
- malformed names, duplicates, oversized areas and slot/payload coordinate mismatches.
- `src/projectile-nbt.test.js`: the native projectile and creeper Fuse/ExplosionRadius records import, restore live, survive a whole region import (report counts them as converted) and survive export→import.
- `src/mob-nbt.test.js`: each of the 22 native mob compounds imports with the native getters' values, restores live, survives a whole region import, and survives export→import (13 browser mobs, including a charged creeper and an owned wolf).

No real Java save with tile entities is checked in. Chest/furnace NBT layouts were read from the pinned JAR's `aow`/`apg` readFromNBT.

## Open

The browser still lacks streaming beyond 128×128, a compact cell payload (the 100,000-edit limit dominates), biome and light import, tile-entity factories beyond chests/furnaces, mob riders and the remaining entity ids, item NBT, pending ticks, and Java write-back. level.dat/player/stats import is in [level-dat](level-dat.md) (one area per import).

## Whole-save import (batch 15)

The browser Import screen's "Java save folder..." now imports every chunk of `region/*.mca`, `DIM-1/region` and `DIM1/region` (`src/whole-save-import.js`). The CLI (`tools/import-java-region.mjs --save DIR --whole-save --out w.blockworld.json`) converts the same whole save and embeds the stored columns as JSON `bases` (`src/whole-save-cli.js`, `src/whole-save-json.js`); without `--whole-save` it stays area-only. Since batch 27 `--whole-save` feeds the importer the same inputs as the browser folder picker (level.dat, all regions, `playerdata`/`players`, `stats`, `data/*.dat`; `--player-file` and `--stats` replace the pick) and runs the same population pass below. The browser Export JSON now also carries `bases` (base64 columns keyed by dimension, capped at 96 MiB of JSON under the importer's 128 MiB limit; columns that do not fit are counted in `wholeSave.basesOmitted` and regenerate from the seed, which the import toast says). The Java ZIP export still keeps its blockworld.json backup without bases, because the Anvil regions carry them. Not browser-checked end to end; covered by `whole-save-json.test.js` and `whole-save-cli.test.js`.

- **Stored full columns.** Each saved chunk becomes a record in a new IndexedDB store `bases` (database version 5, keyed `[world, x, z]`; Nether and End use the `<id>~-1` / `<id>~1` view ids). A record holds the non-empty 16-high sections (block ids and metadata nibbles), the biome bytes and the TerrainPopulated/LightPopulated flags (`src/whole-save-columns.js`). `World.terrainFor` returns a stored column instead of running the generator, so a native chunk loads exactly as saved; chunks missing from the save generate from the seed. Player edits made afterwards are the usual per-column edit records replayed on top of the stored column.
- **Streaming.** One region file is held at a time, converted chunk by chunk through the existing converter (`importJavaRegionArea`, with a stand-in sink world and a one-chunk region file per call), and written in batches of 16 with yields to the event loop. The Import screen shows the chunk count and region file number; Cancel aborts and deletes the partial store. A damaged chunk or region file is skipped and listed in `report.save`. A streamed world hydrates stored columns only for the 8x8 window around the player (exact-key reads).
- **Runtime state.** Tile entities and containers, entities (mobs, items, vehicles, riders, hanging entities, projectiles), pistons and similar records come through the existing converters and are merged into the world record (Overworld) or the dimension record. Rider ids and vehicle ids (boats and carts, which the area importer numbers from 1000000 in every call) are remapped to stay unique across the save, and the `riding` links follow (`whole-save-import.test.js`, two chunks each with a ridden boat).
- **Population.** Imported columns are marked claimed (`populatedColumns`) so the streaming population does not add generated chests, animals or structures to them. The browser's population is stateless per 8x8 cell and cannot run `Chunk.populateChunk` on one imported column, so before batch 27 a chunk saved with TerrainPopulated false loaded bare (see "Populating imported chunks" below for what happens now).  LightPopulated is always exported false. A generated neighbour may still receive overhang (trees, ores) from the cell population that would have run for an imported chunk; this approximates the Java rule that populate also touches the +x/+z neighbours.
- **Export.** The Java ZIP export reads the stored base of every column that was not edited live and writes it back (blocks, metadata, biomes, flag), so an imported world round-trips; the export limit is raised to 16384 columns for an imported world.
- **Evidence.** `src/whole-save-import.test.js` (10 tests): a fake save of region files across the three dimensions built with the repo's NBT and region writers, the codec, batching, claim bits, lazy exact-key hydration, generation of missing chunks, damaged columns, ZIP round-trip and delete. Bytecode-read, not probed: the population neighbour rule. No real 1.7.10 save of large size was imported.
- **Not covered.** Portal-search and `/spreadplayers` height peeks do not see stored columns for non-resident columns; the prefetch worker generates terrain that is then not used for imported columns; the Blockworld JSON export omits stored columns (use the Java ZIP); the `world-import.js` list caps (4096/1024 entries) still apply to the merged record; biomes are stored and exported but not used for rendering; lighting is recomputed. Not full parity.

## Batch 17: the player's own mount (riders track)

- `level.dat` `Player.Riding` of a `Boat` or rideable minecart is imported as before; a `Pig` or `EntityHorse` is now imported as a normal mob flagged `playerRides: true`, and `restorePlayerVehicle` (vehicle-simulation.js) seats the player on it. Batch 20 widens this: every cart variant (furnace, TNT, spawner, hopper, command block) is kept with `rider: true` (`minecarts.js` `mount({saved})`), and every other importable mob becomes a `playerRides` record (cow, spider, zombie... probed mounted by `InterchangeMountProbe`; seating uses `horseSeats` with the mob's size). A chicken, Ender Dragon, Wither, End crystal or baby is reported lost with a note and the player stays at Pos. A nested `Riding` inside the mount is not linked (native `initializeConnectionToPlayer` mounts only the first compound).
- Export writes the flagged mob as the player's `Riding` (never as a chunk entity; native `writeToNBTOptional` is false for a ridden mount). Evidence: `player-riding-reference.json` (`tools/probes/PlayerRidingProbe.java`, native writeToNBT/load/rewrite), replayed by `src/player-riding.test.js`.
- Hanging `Dir` is kept as the raw byte on import (no `% 4`); export writes `Dir` only for 0..3, as native.
- Documented differences: `UUIDMost`/`UUIDLeast` are now written on every entity and the player (batch 20: `src/entity-uuid.js`; mobs, boats and carts keep a persisted `uuid`, short-lived entities get a name-derived one, the player's is `playerUuid` read from level.dat) and kept on import. Zombie and pigman now write the full six-attribute `Attributes` list with their spawn modifiers (`src/mob-attributes.js`; other mobs except horses still write none). Optional mob keys (`AbsorptionAmount`, `CustomName`, `Attributes` for a pig) appear only when set.

## Batch 21: owner and leash links, full Attributes lists (interchange2 track)

- **Owners.** Native wolf and ocelot write `OwnerUUID` as a String (empty when wild) and no `Owner` key; a horse always writes `OwnerUUID` and a separate `Tame` byte (probed, `InterchangeLinkProbe`). Export writes the exported Player's UUID for a player-owned mob (the imported `playerUuid`, else the offline-mode UUID of `Player`, which also names `stats/<uuid>.json`), and a foreign owner string kept on import as `ownerUuid`. Import reads `OwnerUUID`; for a wolf or ocelot with no `OwnerUUID` key the legacy `Owner` name is converted (empty or over 16 characters: used as is; otherwise offline UUID of the name; bytecode-read of `nz.a`, not probed since it needs a server). A horse has no legacy path (probed). An owner equal to the player's UUID is re-linked to the player; any other stays a stored string and is written back.
- **Leashes.** A player holder writes `Leash{UUIDMost,UUIDLeast}` of the player, a knot `{X,Y,Z}` (probed on wolf, ocelot, horse, pig). Import keeps the holder UUID (`leash.holderUuid`) and the area or whole-save assembly (`relinkMobs`) keeps a lead only when it matches the save's player UUID; any other is dropped as native `playerWrongUuid` does, and counted in the report.
- **Attributes.** Every EntityLivingBase now writes the native list for its class (`src/mob-attribute-list.js`, table probed on 29 living classes: maxHealth, knockbackResistance, movementSpeed, followRange, then attackDamage, `horse.jumpStrength` or attackDamage plus `zombie.spawnReinforcements`). Slime and magma cube health is size squared, a tamed wolf writes 20, a baby zombie or pigman adds the fixed `Baby speed boost` modifier (a pigman now writes and reads `IsBaby`). Import applies saved follow range, knockback resistance, zombie maxHealth and reinforcement and kept modifiers; a base the record does not imply is kept as `attributeBases` and written back. Potion modifiers are never saved natively (probed).
- **Evidence.** `interchange-links-reference.json` (125 records), replayed by `src/interchange-links.test.js` including an export, import, export round trip.
- **Not covered.** Movement speed and attack damage bases are preserved, not simulated; native spawned mobs carry a follow range spawn bonus that the port draws only for some mobs; a baby modifier without `IsBaby` is lost; knot holders have no UUID; leads are re-linked only when a player UUID is known. Not full parity.

## Batch 24: spawn bonus, live Attributes, legacy owners (interchange3 track)

- **Spawn bonus.** Natively every EntityLiving class except the cave spider takes the followRange "Random spawn bonus" (`nextGaussian() * 0.05`, operation 1) as its first `Entity.rand` draw in `onSpawnWithEgg`. The port now rolls it for every class (the spider, skeleton and horse rolls hand it back; the zombie and pigman rolls already had it), stores it as a modifier, and exports it.
- **Imported modifiers take effect.** Saved bases and modifiers now drive followRange, knockback resistance, max health and health (every class but wolf, slime, magma cube and horse), the AI move speed and melee attack damage. Native clamps: max health is not capped at 2048, follow range is capped at 2048, knockback at 1, and speed has a floor of 0. Unknown attribute names are dropped. HealF is read after Attributes.
- **Baby boost and held items.** An adult zombie or pigman keeps a saved "Baby speed boost" and moves at 1.5x. The held item's Weapon/Tool modifier (UUID `cb3f55d3-…`) applies only while the mob is live and is never saved.
- **Legacy `Owner`.** This is PreYggdrasilConverter on an online-mode IntegratedServer with no network. A name of 1 to 16 characters becomes its offline UUID, with the name as written. An empty name, or one of 17 or more characters, is kept. `OwnerUUID` wins over `Owner` even when empty and is never trimmed. A dedicated offline server lower-cases the name, and an online one stores "" when the lookup fails; the port models neither of these, nor usercache.json.
- **Evidence.** `interchange-spawn-reference.json` (250 records from `tools/probes/InterchangeSpawnProbe.java`, written by `tools/verify-interchange-spawn.mjs`), replayed by `src/interchange-spawn.test.js` (11 tests).
- **Not covered.**
  - Wolf, slime and horse maximum health ignore saved max-health modifiers.
  - The pigman's ground speed is fixed, so its boost has no effect.
  - The horse's speed comes from horse-live.
  - The bonus chest timing was already at world creation, so it was not changed this batch. Torch onBlockAdded was not probed.

## Populating imported chunks (batch 27)

`src/imported-population.js` runs `Chunk.populateChunk` at import time for every stored Overworld column the save marked TerrainPopulated=false, as a post-pass of `importWholeSave` (browser: `readBases`/`writeBases` on IndexedDB; Node CLI: the same code over the JSON `Map` store in `whole-save-cli.js`). Imports without `readBases` (or `populate: false`) keep the old bare behaviour and say so in `notImported`.

- **Rule.** `populationPlan` reproduces the native call order: a populate fires for a target whose +x, +z and +x+z neighbours are loaded, checks (x,z), (x-1,z), (x,z-1), (x-1,z-1) in that order, with the rectangle loaded x-outer, z-inner. Neighbours that the save does not store are the generator's terrain with caves and ravines (`StreamingPopulation.original`), exactly what Java would generate there. Populated chunks are never repopulated; their cells change only where a neighbour's populate writes into them (the +8 offset spills into +x/+z/+x+z), as natively.
- **Generators.** Default, LargeBiomes, Amplified and Superflat, MapFeatures on (generation 16) or off (17), via the level.dat's generator (`levelGenerator`).
- **Write-back.** Changed cells are applied to the stored columns (batches of 16, LRU of 48 columns in memory) and the flag is written TerrainPopulated=true, so the Java export writes the populated chunk. Chests, dispensers, spawners, dungeon minecart chests and liquid pending ticks the populate produced are merged into the world record; animals, villagers, swamp-hut flower pots and the non-liquid ticks (fire, falling blocks) are kept as runtime records since batch 28 (see "Nether, End and kept records"); only ticks of other blocks are counted in `report.population.dropped`. A populate that needs a cell the port cannot hold (unmapped block or id above 255) is skipped whole and counted in `skipped.unmapped`; `skipped.noNeighbours` covers a chunk on the edge of the stored area (+x/+z neighbours absent from the save are generated, so this stays 0 for Overworld saves).
- **Nether and End.** Populated since batch 28 (next section); `report.population.unpopulatedNetherEnd` still counts the chunks the save marked unpopulated.
- **Native evidence.** `tools/probes/InterchangePopulateProbe.java` drives the real `Chunk.populateChunk` through a `java.lang.reflect.Proxy` over the chunk provider. `tools/verify-interchange-populate.mjs` replays six scenarios (all unpopulated, checker pattern, holes with LargeBiomes and MapFeatures off, Amplified with flowing lava, structures at seed 17 and a seed with holes: 144 native populate calls) and compares call order, populated flags, per-chunk block hashes, chest and spawner counts; `public/research/interchange-populate-reference.json` is its output. Batch 28 closed the divergence below with the stored-cell overlay: a stored cell cannot keep level-0 flowing fluid, so flowing cave lava at level 0 reads as still; the `exactInput` hook isolates it (hashes equal with exact input).
- **Cost.** Time is about 50 ms per populated chunk in Node (the 25-chunk synthetic save: 1.3 s of a 3.0 s import); memory is bounded by the 48-column LRU (about 128 KiB per column) plus the merged lists. Imports of saves with many unpopulated chunks (a freshly generated 1.7.10 world has a ring of them) pay that per chunk.

## Nether, End and kept records (batch 28)

`populateImportedColumns({dimension: -1 | 1, seed, ...})` runs the same native trigger (`populationPlan`) over the stored Nether and End columns (`src/imported-population-dims.js`), with `ChunkProviderHell.populate` / `ChunkProviderEnd.populate`. Stored columns of both dimensions are keyed by native chunk coordinates (no generator origin).

- **Nether.** One `ChunkProviderHell` per import: its hellRNG is the constructor state (a server that has just started, no `provideChunk` reseed) and carries over every populate call exactly as natively; World.rand is one `JavaRandom(0)` per import (natively time-seeded; it only draws fire tick delays). Fortress starts are searched with `MapGenNetherBridge.generate` over the four chunks of the populate window (natively `provideChunk` finds them and Fortress.dat keeps them). Terrain a populate reads outside the stored set is the generator's own (lazy halo, writes dropped); a populate that reads a stored chunk the cache lacks is retried with the generators rolled back to their state before the attempt (the retry used to double-draw the RNG).
- **End.** `ChunkProviderEnd.populate` draws from World.rand, time-seeded natively; the model is the stable per-chunk seed `seed ^ (x * 341873128712 + z * 132897987541)` that `dimension-world.js` uses. Spike crystals and the dragon (chunk 0,0) become `ender_crystal` / `ender_dragon` entity records of the End blob (`dragonSpawned` is already set by the import).
- **Native evidence.** `tools/probes/InterchangeDimPopulateProbe.java` generates chunk rectangles with the unchanged `provideChunk` (real `MapGenNetherBridge` search) and loads them through the unchanged `Chunk.populateChunk` (`apx.a(apu,apu,II)`) over an `apu` proxy; `tools/verify-interchange-dim-populate.mjs` replays nine scenarios (Nether: all unpopulated, checker, holes, two 12x12 seeds; End: origin with the dragon, checker, negative holes, 10x10: 406 native populate calls) through `populateImportedColumns` and asserts call order, flags, per-chunk block hashes, spawners, chest counts, End entities and the scheduled-tick counts (output: `public/research/interchange-dim-populate-reference.json`, replayed by `src/imported-population-dims.test.js`). Native-modelled: the populating Nether provider is fresh (restart state), World.rand for the End is seeded per chunk; neither is natively fixed because natively both are time-dependent.
- **Stored-cell overlay.** A stored cell is one internal id plus 4 bits of meta, which cannot tell a level-0 flowing fluid from a still one, hardened lava with a level from flowing lava, or carry chest facing. A column record may now carry `orig`, a sparse sorted list `[index, id << 4 | meta, ...]` (JSON key `o`) holding the exact original state of every cell whose original differs from what the registry implies for the cell (`impliedOriginal`, `src/stored-overlay.js`). Columns written before batch 28 have no `orig` and read as before. The importer (`ColumnSink`, fed by `region-import.js`) writes it for saved chunks; the populate reads it first and keeps it current for every cell it writes; the Java export applied it only to fluids in batch 28, and from batch 29 to every unedited cell (see "Saved TileTicks and export overlay").
- **Kept records.** Animals and villagers a populate spawns (`SpawnerAnimals.performWorldGenSpawning`, village NPCs) become entity records (`EntityWorld.create` + `serializeOne`, local coordinates); swamp-hut pots go to `pots`; scheduled ticks go by block: liquids to `fluidTicks`, fire to `fireTicks`, sand and gravel to `fallingTicks`. A fluid tick stays on whatever fluid its cell holds after the populate (`BlockLiquid.onBlockAdded` turns a closed pocket static). `report.population` counts `animals`, `villagers`, `pots`, `fireTicks`, `fallingTicks`, `droppedTickIds` and a `dimensions` entry per populated Nether/End. Ticks of saved chunks (`TileTicks`) were only counted in `report.scheduledTicks` until batch 29 (see "Saved TileTicks and export overlay").
- **Furnace lit state.** Natively the furnace block id is the lit state (61 unlit, 62 lit) and `TileEntityFurnace.updateEntity` changes it only when its burning flag flips. A furnace record now carries an optional `lit` from the saved id; `scene.setFurnaces` and the export use `lit ?? burn > 0`, and `Survival.tickFurnaces` drops `lit` when the burn flag flips (2-line hunk). The synthetic round trip no longer turns the unlit furnace (61, BurnTime 120) into 62 in the Nether and End.
- **Synthetic save.** `make-synthetic-save.mjs` now leaves Nether chunk (-1,-2) and End chunk (-1,-1) unpopulated; the round trip reports `populatedByImport` for both.

## Peeks over stored columns (batch 27)

`src/stored-peek.js` indexes a whole save's stored columns once per world and dimension (one pass over the stored sections, no full decode): the top block +1 per cell for `/spreadplayers` (`topY`, CommandSpreadPlayers rule: first non-air block below 256, y >= 1, 257 over an empty column) and the columns holding a nether portal block for the Teleporter's 257 x 257 search (`TerrainPeek.portalColumns`/`column`), with at most 256 decoded portal columns kept so the search can read them. Cost: 512 bytes per stored column plus 128 KiB per kept portal column, built in the background when a whole-save world opens (`DimensionLive.warmStored`) and on the first peek. Limits: `topY` is synchronous, so it answers from the finished index and falls back to generated terrain while the index builds; post-import edits to a column that was evicted from residency are not seen by the index (resident columns and still-cached edits are).

## List caps (batch 27)

`world-import.js` no longer truncates the merged runtime lists at 4096 (1024 for minecarts, boats and villages): `LIST_CAP = 1 << 20` per list. The merged record is built in memory at import, then split per column at the first persist (`splitRuntime`) and hydrated per column afterwards; cost is roughly 150-400 bytes of heap per entry. The loaders that read a live window still bound what runs at once (items 512, mobs 256, drops 512 per area in other modules), and those are unchanged.

## Synthetic save (batch 27)

`tools/make-synthetic-save.mjs OUT_DIR` writes a 1.7.10-format folder (96 Overworld chunks over two regions with a third of the columns unpopulated, a 16-chunk Nether and a 9-chunk End, chests, signs, furnaces, hoppers, spawners, skulls, pigs, cows, zombies, items, chest minecarts, paintings, a player, stats). It is written by this repo's generators and Anvil writer, not by the Java classes. `tools/roundtrip-synthetic-save.mjs SAVE_DIR` imports it through the browser path (fake IndexedDB), exports it and compares. Result for the default save: no chunk missing, every tile entity and entity id preserved in all three dimensions; the Overworld's 25 unpopulated chunks were populated (3 spawners and 3 dungeon chest carts added; 8 animals dropped); a lit-furnace normalisation (61 to 62) in the Nether and End; changed cells in the Overworld are populate writes (including those spilling into already populated neighbours). Lost on export: LightPopulated (always false), the player UUID (offline-mode UUID of "Player" replaces the file name), AI/RNG state and populate-time animals (pending ticks round-trip since batch 29).

## Saved TileTicks and export overlay (batch 29)

- **Native read and write (bytecode-read, plus the unchanged `ChunkNbtProbe` payload reference).** `AnvilChunkLoader` reads each `TileTicks` entry `{i, x, y, z, t, p}` through `WorldServer.func_147446_b` (`mt.b`, scheduleBlockUpdateFromLoad): no chunk-exists test, priority always set, scheduled time = world time + `t` for a non-air block, added only when no entry with the same x, y, z and block is present. It writes the entries of `getPendingBlockUpdates` (`mt.a(apx, false)`) whose x and z lie in `[chunk*16-2, chunk*16+18)`, tree set then this-tick list, as `t = scheduledTime - worldTime`. A tick within 2 blocks of a border is therefore saved in two chunks. Header of `src/tile-ticks.js` has the details.
- **Import.** `src/tile-ticks.js` maps each tick by original block id: water and lava (8 to 11), fire (51) and falling blocks (12, 13, 122, 145) become `fluidTicks`, `fireTicks`, `fallingTicks` envelopes (time 0, `delay = t`, with the original id as `orig`); every block the live redstone engine schedules (those with an `updateTick` behaviour plus dispensers, droppers, command blocks and detector rails) becomes an entry of the record's `redstone.pending` `[x, y, z, id, t, p, serial]`, so a repeater mid-delay resumes with its delay and priority. Powered repeaters (94) go to `redstone.lit`. A border tick saved in two chunks is kept once (native hash-set rule; `report.ticks.duplicates`); ticks outside the imported area are `outsideArea`; ids the port does not schedule are tallied in `report.ticks.dropped`. Whole-save imports merge per dimension (`mergeTickState`). `world-import.js` sanitises the `redstone` field (strict shapes, capped lists, no RNG or events); `redstone-runtime.js` restores the pistons record separately when the import's `redstone` has none.
- **Export.** Pending ticks from all four lists are written with their original id, `t = delay` and `p` (priority kept for redstone; 0 for fluid, fire and falling), sorted by t, p; ticks within 2 blocks of a border are also written into the neighbouring owned chunk, as natively.
- **Overlay precedence.** For a cell the runtime has not changed, the export now writes the stored `orig` state. The runtime wins only where it owns the state: farmland whose moisture is tracked and not 7, a furnace with a tile record, a repeater when the record has a lit set. Otherwise the cell falls back to `toOriginal` as before. Fluid ticks only force flowing ids on entries that were flowing (8, 10) or have no `orig`, so a still lava cell with a tick stays 11.
- **Synthetic round trip (before / after).** `make-synthetic-save.mjs` now adds a y=210 platform per furnished chunk (moistened and dry farmland, repeater and powered repeater with ticks, comparators, torch, flowing and still water, still lava, sand, fire, dispenser, chest facing). TileTicks identical in/out: Overworld 0 of 162 before, 162 of 162 after; Nether 0 of 9 to 9 of 9; End 0 of 9 to 9 of 9 (extra ticks out are populate-produced fluid and fire ticks and the border copies). Changed-cell kinds 27 to 21 (cell total 19109 to 19103): the platform drift (farmland 5 to 7, powered repeater 94 to 93, water level 3 to 9) is gone; the rest are populate writes.
- **Populate missing exact cell.** `tools/fuzz-imported-population.mjs` wraps `mapBlock` and records every non-exact result during `populateImportedColumns`. About 60 seeds (about 2900 populate calls) over unpopulated, checkerboard and holey layouts gave zero `skipped.unmapped` and no non-exact results; no case where a populate step hits a missing exact cell was found. Not a proof: only the seeds tried.
- **Batch 30 (interchange7).** `tools/probes/TileTicksProbe.java` runs the unchanged `AnvilChunkLoader` reader and writer on a real `WorldServer` (`public/research/tile-ticks-reference.json`, 24 scenarios, replayed in `src/tile-ticks.test.js`): the pending list is a TreeSet ordered by time, priority, creation order; air keeps time 0, the same x/y/z/block is added once; the writer box is `[c*16-2, c*16+16)` (batch 29 had +18, fixed in `spreadTicks`). Comparator `OutputSignal` (int, `getInteger`) is imported into the live redstone `comparators` and exported for blocks 149/150.
- **Outside the chunk box.** Natively a tick whose own chunk is not loaded at its due time is dropped (`WorldServer.a` with radius 0, bytecode-read); the port drops it at import and counts it as `outsideArea`. It differs only before the due time, when a native save would still write it back.
- **Priority.** Only repeaters and comparators schedule with a priority; fluid, fire and falling always use 0. It shows only in foreign saves; the port uses `p` of those kinds to order the load and exports 0.
- **Horse chest Items** (`HorseItemsProbe`, `horse-items-nbt-reference.json`): slots 2..15 or 2..size-1 only; counts 0 and negative are kept, above 64 lowered to 64; an unknown id clears the slot; negative Damage reads 0.

- **Limits.** Fluid, fire and falling priority is not stored. Order between kinds at the same time and priority is not kept (separate lists). Ticks on air, unknown ids or y outside 0..255 are not kept. A save taken mid tick (ThisTick) is not modelled. Farm moisture on export is a heuristic for tracked cells only. A lit repeater is detected from its block id (94).

## Native Nether and End populate seed dependencies (bytecode-read, batch 29)

- **Nether (`aqv` = ChunkProviderHell).** The constructor `aqv(World, long seed)` sets `i = new Random(seed)` (the hellRNG) and builds the noise octaves from it. `provideChunk` (`c(II)`) first calls `i.setSeed(x * 341873128712L + z * 132897987541L)` (no world seed in that value), then fills the terrain and calls the fortress search; `populate` (`a(apu, int, int)`) passes `i` to the fortress search and the feature generators it calls (the generator calls read `i`) and uses World.rand only through the fire block's tick scheduling (not re-read in this pass). It does not reseed. So the hellRNG at a populate is the state the last `provideChunk` of that provider left it in, advanced by every draw since (earlier populates, later `provideChunk` reseeds). That depends on the order in which the server generated or loaded chunks since it started; chunks loaded from disk do not call `provideChunk`. The importer's model (fresh provider, constructor state, carried across calls in the plan's order) is one valid history, not the native one for a given real save.
- **End (`ara` = ChunkProviderEnd).** `provideChunk` reseeds its own `i` with the same coordinate hash, but `populate` calls the biome's decorate with `World.rand` (`ahb.s`), which natively is time-seeded when the server starts. So End population is not a function of seed and chunk natively; the port's per-chunk seed `seed ^ (x * 341873128712 + z * 132897987541)` is a model.
