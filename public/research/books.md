## Verified by running the original classes (probe)
- Book and Quill: id 386, stack 1, Miscellaneous tab (index 4), no glint. Written Book: id 387, stack **16**, **no creative tab**, always glints.
- Names: "Book and Quill" / "Written Book" (en_US); a written book is named by its title when non-empty (not trimmed), with the gray line "by <author>" when the author is non-empty.
- Textures `book_writable`, `book_written`.
- Tag validation (`ael.a`, `aem.a`): `pages` must be a list, each page at most 256 chars, no page-count limit; a written book also needs a string `title` of at most 16 chars (empty allowed) and a string `author`. 21 cases.
- Recipe: shapeless book + ink sac (dye damage 0) + feather, in any order, 2x2 or 3x3. RecipeBookCloning: exactly one written book plus one or more writable books and nothing else; the result is a written book with count writables + 1 and a copy of the tag and display name. A written book without a tag throws a NullPointerException in the original (the port makes no result).
- FontRenderer widths for codes 32-126 and the word wrap (`listFormattedStringToWidth`, `sizeStringToWidth`, section-sign codes, bold +1) at widths 116/118/104/160 (64 records).

## Verified by driving the unchanged GuiScreenBook (batch 18, `BookGuiProbe`)
The probe runs `bfe` with the real FontRenderer (reading the shipped `ascii.png` and `glyph_sizes.bin`, both unicode flags) and test doubles for Minecraft (displayGuiScreen, font, texture manager, net handler), GameSettings, LWJGL (`Keyboard`, `GL11` no-ops, `tools/probes/lwjgl-doubles/`) and the player (a real `yz` with a GameProfile). The button list is emptied during `drawScreen` so only the screen's own calls are recorded: the `drawTexturedModalRect` blit and the FontRenderer `drawString` / `drawSplitString` calls. Sent MC|BEdit / MC|BSign packets are decoded with the original `PacketBuffer.readItemStackFromBuffer`. 32 scenarios (about 240 steps) and 60 wrap records are replayed in `src/book-gui.test.js` step by step against `BookScreen` (page, page count, signing, modified flag, title, page list, which buttons are visible and enabled, drawn text and coordinates, closes, sent stacks).
- Drawing: the 192 x 192 `book.png` blit at (centre - 96, 2); page text is one `drawSplitString` at (x + 36, 34) width 116 with the cursor (`black _` for 6 ticks, `gray _` for the next 6, by `ticks / 6 % 2`); "Page x of y" is a `drawString` ending 44 px before the page's right edge at y 18 (no cursor or text when read-only); the sign screen draws "Enter Book Title:" centred at y 34, the title plus blinking cursor centred at y 50, `§8by <name>` centred at y 60 and the warning as a split string at y 82 (all in the 116 px column at x + 36, colour 0, no shadow).
- Keys: Backspace removes one char (page or title); Enter and keypad Enter insert `\n` (title screen: sends when the title is non-empty, with whitespace-only titles allowed); a char is inserted only while the page with `black _` still wraps within 118 px height and stays under 256 chars (a full page holds at most 255 chars; 'W' stops at 246, 13 newlines fit); title at most 16 chars; `§`, DEL and control characters are not typeable; Escape closes without sending.
- Paste (ctrl+V reads the AWT clipboard, which the headless probe cannot set, so the private `pageInsertIntoCurrent(String)` is called directly): the clipboard text is inserted **unfiltered** (section signs, tabs and control characters included; `ChatAllowedCharacters` only filters typed chars, and ctrl+V as a char is below 32, so it types nothing in the title) and a chunk that would break the 118 px / 256 char rule is rejected whole. The port's browser paste handler now inserts the raw text (CRLF normalised to LF, as AWT does) instead of stripping `§` and controls.
- Buttons: Sign (3) and Done (0) or, while signing, Sign and Close (5, enabled only while `title.trim()` (Java trim, up to U+0020) is non-empty) and Cancel (4); read-only has just a 200 px Done. Next shows while not signing and (not on the last page or editable); previous while not signing and page > 0. Clicking Next on the last page of an editable book adds a page (to 50) and marks it modified; 60 clicks end at page 50 of 50.
- Done / Sign and Close send only a `modified` book, trailing empty pages after the first are dropped (the page list in the tag is edited in place); Sign and Close with unchanged pages still sends once a title char was typed (typing marks it modified); Done with no change sends nothing. The signed stack is `{id 387, count, damage 0, tag {pages, author = player name, title = trimmed}}`; no other tag keys, and **no generation tag** (1.7.10 has none; the written tag keys in every sent stack are exactly `pages`, `author`, `title`, plus `display` when the stack was renamed).
- Constructor quirk: a stack with any tag but no `pages` (for example a Book and Quill renamed in an anvil) gets an empty page list, so typing changes nothing on pages 1 and 2 until a page exists (the port reproduces this through `hasItemTag`); an untagged Book and Quill starts with one empty page.
- Cloning (`RecipeBookCloning`) results, probed in `book-reference.json` (`keys` per tag): the copy holds exactly the written book's keys (`pages`, `author`, `title`, `display`), no `generation`; the port's `bookCloneResult` adds none either.
- Wrapping with non-ASCII text: 60 records over accented Latin, Latin-1 punctuation, CJK, kana, Cyrillic, Arabic, Hebrew, Hangul, block and box symbols, control/odd code points and section codes at widths 116/118/60 for both unicode flags match `font-renderer.js` + `books.js` (the port already used the real width tables, not a flat 6; the batch 17 note was stale).

## Approximations and gaps
- `BookScreen` is a port that is replayed against the original `bfe` (batch 18); the DOM drawing in `book-ui.js` follows the probed draw list (`bookDrawList`) but pixels were not compared with a GL render. The page arrows (`bff`: 23 x 13, texture u 0 / 23 on hover, v 192 forward / 205 back at (x + 120, 156) and (x + 38, 156)), the hover state, button textures, and the bidi (right-to-left) flag stay bytecode-read (the flag is covered by a test of `splitLayout` in `server-handlers.test.js`). The server handlers `MC|BEdit` / `MC|BSign` are no longer only bytecode-read: batch 30 runs the unchanged `NetHandlerPlayServer` with test doubles (`tools/verify-server-handlers.mjs`, `server-handlers-reference.json`, 41 book cases) and `applyBookEdit` / `applyBookSign` replay them.
- The real ctrl+V reads the OS clipboard; the port reads the browser `paste` event (or a `clipboard()` callback for the ctrl+V char), which is the closest equivalent.
- The client stack is not turned into a written book by the screen itself (the original does it before sending); the host applies `applyBookSign` to the held stack, which gives the same result in the single-process game.
- Author: this build has one fixed local player named "Player" (`PLAYER_NAME`, `death-messages.js`; the same name the chat, stats, village and scoreboard code use). The screen takes it from `playerName` and the held stack gets it through `applyBookSign`; it stands in for the session username (`EntityPlayer.getCommandSenderName`) and the signed author is the same string the title screen shows as "by Player". The Written Book is craftable only by signing or cloning, and `/give` with a data tag.
