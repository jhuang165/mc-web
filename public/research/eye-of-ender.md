# Eye of Ender, end portal block and portal frame use (1.7.10)

Evidence: `tools/probes/EyeOfEnderProbe.java` runs the unchanged original classes (acn ItemEnderEye, zd EntityEnderEye, akt BlockEndPortal, aku BlockEndPortalFrame, apo TileEntityEndPortal, ave/aug stronghold generator) against a world double. `tools/verify-eye-of-ender.mjs` checks the client JAR SHA-1, class digests and record counts, and writes `public/research/eye-of-ender-reference.json` (297 records). Items marked "bytecode-derived" were read from javap, not executed.

## Behaviour

- Item 381 is internal 1960 "Eye of Ender". Recipes: ender pearl + blaze powder (shapeless); eight obsidian around an eye make an ender chest (1941).
- Right-click in the air: finds the closest stronghold (coordList entries `((cx<<4)+8, 64, (cz<<4)+8)`, smallest squared integer distance including y, strict `<`). No stronghold: nothing happens, nothing consumed. Otherwise the eye spawns at the feet position, `random.bow` plays (volume 0.5, pitch 0.4/(rand*0.4+0.8)), aux 1002 fires, and the stack is consumed unless creative.
- Flight (probe, 11 flights x 81 ticks): target is the exact point when horizontal distance <= 12, else 12 blocks along the line at posY+8. Speed `f + (f1-f)*0.0025`, x0.8 when closer than 1. Vertical drift 0.015 toward the target height. One portal particle per tick (four bubbles in water). At age > 80 the eye dies: 80% (`nextInt(5) > 0`) drops as an item entity, otherwise aux 2003 shatter effect at the rounded position (bytecode-derived effect).
- Right-click on a portal frame: if empty, sets the eye bit (meta 4), consumes the item, spawns smoke and runs the ring check. Only the full 12-frame ring with all eyes fills the 3x3 with portal blocks (probe: 256 x 12 ring outcomes, 400 mask samples). A frame that already has an eye leaves the stack unchanged.
- End portal block (BLOCKS slot 149, original 119): hardness -1, light 15, not solid, no drops, bounds (0,0,0)-(1,1/16,1), unbreakable by survival. Rendered by `src/end-portal-renderer.js`.
- Region import/export: block 119 and the `Airportal` tile entity round-trip.
- Stronghold portal room 10% eye chance per frame is present in the existing port (`StrongholdPortalRoom`).

## Gaps

- Batch 68 (docs sweep): the End dimension exists now. Contact with the end portal block calls `travel(END)` for free entities only (`src/dimension-live.js`, `DimensionLive` per-tick portal check; riding and remote do nothing, as in the probe); see `dimensions.md`. The eye is also saved in flight, `/summon`ed (and `/give`n, both in `command-data.js`) and run on the server (`src/multiplayer/server-eyes.js`).
- Generated stronghold starts are not consulted, only the coordList (as in a fresh world).
- The base `Entity.onEntityUpdate` is not modelled in the pure tick; the in-water flag arrives through a hook.
- Creative restoration of the used eye is bytecode-derived (ItemInWorldManager), not probed.
- The portal TESR (bmt) is approximated with layered starfield planes; the eye-linear texgen is not reproduced.
- Batch 80 renderfx80: the approximation is replaced. `src/end-portal-renderer.js` ports `bmt` (TileEntityEndPortalRenderer): 16 passes on one quad at y + 0.75, pass 0 `end_sky.png` (shade 0.1, depth 65, scale 0.125, alpha blend), passes 1-15 `end_portal.png` additive (depth 16 - i, scale 0.5 for pass 1 and 0.0625 after, shade 1 / (17 - i)), rotation (i * i * 4321 + i * 9) * 2 degrees, the colour from Random(31100) (three floats per pass, pass 0 included, then white for pass 0) as Tessellator bytes, the scroll (getSystemTime % 700000) / 700000. WebGL has no fixed-function texgen, so the fragment shader computes the same coordinates in closed form (`endPortalUv`): the eye ray through the fragment meets a plane `depth` blocks below the portal, giving each layer its own parallax. Executed: `tools/probes/RenderFx80Probe.java` runs the unchanged `bmt` on a stub GL11 (5 camera fixtures, every texgen mode and plane with its modelview, the texture matrix and Tessellator vertices per pass) into `renderfx80-reference.json`; `src/renderfx80-b80.test.js` replays the GL pipeline (object planes, eye plane through the inverse modelview, texture matrix, divide by q) against `endPortalUv` and checks binds, blends, quads and colour bytes. The match is within the float rounding of the replayed matrices; far from the origin that rounding is large (the eye plane is set under a modelview translated to the camera's world position), so native GL itself jitters there and the port does not reproduce that jitter. The 16 blended passes are drawn as one opaque shader pass (both textures are opaque: pass 0 replaces, the rest add; clamped once, not per pass). Each pass takes the lightmap at the tile's own brightness and its own fog, as the fixed-function passes do. The eye point is the drawn camera plus `near` along the view (ActiveRenderInfo's unprojected near-plane centre); the port's first-person camera has no 0.1 back-off (`orientCamera`), so it sits 0.1 block ahead of native. The 64-block cull (TileEntity.getMaxRenderDistanceSquared 4096 from the cell centre) is in the vertex shader; the scan window is still 20 x 12 blocks around the player. 1.7.10 has no end gateway; the frame is RenderBlocks type 26, not this renderer. Not checked in a browser.
- Batch 81 render81 (2026-11-18): three of the batch 80 gaps are closed. (1) Per pass: the shader writes each of the 16 passes as an 8-bit colour-buffer value (clamp, x 255, round) before adding the next, as the fixed-function blend does. `endPortalPixel` is the same replay in JS; `src/render81-b81.test.js` runs the generated GLSL through a small GLSL ES 1.00 interpreter (`src/glsl-mini.js`) and matches it exactly on tie-free inputs, and shows the single clamp differs. (2) Eye point: in first person (awake) the texgen eye is backed off 0.1 along the player's pitch/yaw axis, then moved `near` (0.05) forward. This is `orientCamera`'s glTranslatef(0, 0, -0.1) before the pitch/yaw rotations and ActiveRenderInfo's winZ 0 unprojection (EntityRenderer `blt.h(F)` and `blt.a(F,I)`, bytecode-read). Third person and sleeping keep the drawn camera's near point. (3) Scan: `EndPortalIndex` searches each meshed column's block array once per mesh (the scene's chunk group is the stamp) and only polls brightness per frame, so every resident portal tile is drawn within the vertex shader's 64-block cull. That is the whole loaded window, not the old 20 x 12 box. The shader stays GLSL ES 1.00: no loops, uniform arrays, precision statements or conditional texture reads; the layer constants are literals. Not checked in a browser or on a real GPU.
