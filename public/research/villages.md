# Java 1.7.10 villages (GEN-05c)

Status: **partial**. `src/village-generator.js` ports 1.7.10 village generation as a standalone module and
`src/village-generator.test.js` replays the unchanged pinned classes' output exactly for the 25 recorded cases below.
It is not called from live world generation, and this is not a parity claim for villages or structures.

## Evidence

`node tools/verify-villages.mjs` compiles `tools/probes/VillageProbe.java` against the SHA-1 pinned
`minecraft-1.7.10.jar` (`e80d9b3bf5085002218d4be59e668bac718abbc6`) and runs it on the installed JDK 19.0.1. The probe
executes the original, unmodified classes:

- `MapGenVillage` (`avn`), including its own `size`/`distance` option parser, and `MapGenVillage.Start` (`avo`);
- `StructureVillagePieces` (`avp`) with its weighted piece list and picking (`avu`), Start (`awa`), Well (`awf`), Path
  (`awb`), Torch (`avt`), House1 (`avq`), Church (`avy`), House4Garden (`avw`), WoodHut (`avx`), Hall (`avv`), Field1
  (`avr`), Field2 (`avs`), the Blacksmith with its chest loot (`avz`) and the Library (`awc`);
- the village base class `awd` (desert substitution, `getAverageGroundLevel`, `spawnVillagers`) with a real
  `EntityVillager` (`yv`), `ItemDoor.func_150924_a` (`ach`), `WeightedRandomChestContent`, the structure framework
  (`aqx`, `ave`, `avm`, `avk`, `asv`) and the real `WorldChunkManager` (`aib`).

The World is an explicit block-access double over analytic fixtures (`flat`; `hills` with water up to Y 63, leaves and
tall grass; `dunes` with sand over sandstone) and a chosen `WorldProvider` ground level (64 normal, 4 flat world).
`MapGenStructureData` loading returns null and saving is ignored. Each case runs the unchanged driver
(`MapGenBase.func_151539_a`) from one centre chunk, then populates every chunk that covers a sizeable start once, in the
JVM's start-map order, with the `ChunkProviderGenerate` populate seed. Every populate call records the result, the
accepted-write count and SHA-1, the ordered service-call count and SHA-1 (block read 0, isAir 1, setter 2, tile lookup 4,
entity spawn 5, `getTopSolidOrLiquidBlock` 6, neighbour notification 7), the villager spawn records and the next
`nextLong` of the Random. `public/research/village-reference.json` (about 0.7 MB) keeps those digests for all chunks and
the complete write lists for 58 chunks, plus the full piece lists of every start, the chest contents and the post-populate
piece hashes. It also pins the class SHA-256 values and SRG symbols used.

`node --test src/village-generator.test.js` replays all of it in the JS port: **5 tests pass**.

negative chunk coordinates, an off-candidate driver centre, three villages generated by one driver call (distance 12,
overlapping pieces and shared state), a flat-world provider (ground level 4), sizes 1 to 3 and invalid starts.

### World adapter additions

`structure-framework.js` is untouched. The village module needs these from the world (documented in its header):
`getTopSolidOrLiquid(x, z)`, `getAverageGroundLevel()` (64, or 4 for a flat world) and an optional
`notifyBlocksOfNeighborChange(x, y, z, id)`; villagers go to `spawnEntity` as
`{type: "Villager", x, y, z, profession}`. The test's `VillageWorld` extends `RecordingWorld` with the probe's fixtures
and extra call kinds, because `structure-framework-fixture.js` is also left untouched.
Gaps worked around inside the village module (not in the framework): the desert-substituting `placeBlock`,
`fillWithBlocks` and downward-fill overrides, the village door facing logic and the average-ground-level helper.

## Limits and remaining work

- Batch 69 (docs sweep): villages are wired into live generation for finite generation 14 and streamed generation 15 worlds (`src/main.js` version note; `src/village-generator.js`).
- `canSpawnStructureAtCoords` also reseeds `World.rand` natively (`setRandomSeed`); that mutation is not tracked.
- Neighbour-update callbacks (door placement notifications) are only forwarded to an optional adapter hook; block
  physics, lighting, fluid ticks and farmland/torch tile behaviour are not modelled.
- Batch 69 (docs sweep): villagers have AI, trades, breeding, golems and siege logic (`src/village.js`, `src/village-ai.js`, `src/villager-trading.js`, `src/village-siege.js`; see [village](village.md)). Original text: villagers were data records only.
  no `VillageCollection`/doors tracking.
- No NBT persistence (`MapGenStructureIO`, `MapGenStructureData`, piece save/load, `ViStart` etc. round trip).
- Fixtures are synthetic and analytic, not the native terrain generator; ground height, water and leaves reflect what
  the fixtures contain. Replaying villages over real terrain chunks (as the mineshaft replay does) is not done.
- The Java `HashMap` start order is that of the recording JVM (19.0.1); the JS `StructureMap` reproduces Java 8+ order.
- Unrecorded combinations remain unverified, for example sizes above 3, distances other than 12/32, amplified/flat world
  types for the generator (only the biome manager type changes).
- Villages from modded options, village generation in the Nether/End and the `Village` structure id are out of scope.
