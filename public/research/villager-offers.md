# Villager initial offer generation

This standalone kernel ports the initial recipe generation performed by the unchanged Minecraft Java 1.7.10 `EntityVillager.t(int)` method. It accepts an original 1.7.10 profession ID (`0` farmer, `1` librarian, `2` priest, `3` blacksmith, `4` butcher), the villager's `JavaRandom`, and an optional number of new offers to merge. Stack IDs remain original numeric IDs, so the layer does not depend on this app's live item registry.

The implementation includes the native candidate tables, probability checks and ordering, item quantity ranges, empty-list gold-ingot fallback, priest enchantment offers, librarian enchanted-book offers and prices, candidate shuffle, and the `MerchantRecipeList` merge behavior for selected new offers. It uses the existing enchantment registry and random-enchantment helpers. Generated recipes begin with zero uses and seven maximum uses, as native `MerchantRecipe` does.

`EntityVillager`'s `Random` stream is supplied by the caller. Java's `Collections.shuffle` uses a separate static `Random`; the kernel models that as a separate module-shared stream by default and accepts `shuffleRandom` injection for deterministic replays. The native probe seeds that JDK singleton independently per case. Shuffle results and both post-call RNG positions are checked against native output. The fixtures were captured with the project's Java 19 runtime; the pinned 1.7.10 classes and JAR SHA1 are recorded in [villager-offers-reference.json](./villager-offers-reference.json). Runtime-specific `Collections` implementation details outside that tested runtime are not asserted.

The reference corpus includes 40 seeds per profession and both full-candidate and one-offer calls (400 cases, 1,032 returned recipes). The probe projects ordinary enchantment levels in numeric-id order; tests normalize only that observed projection, while production preserves the existing enchantment helper's list order. This corpus does not independently verify raw `ench` NBT list ordering. It is generated by executing the original class, not used by production code. Run `node tools/verify-villager-offers.mjs` to regenerate it, then `node --test src/villager-offers.test.js` to replay the cases.

This is a standalone generation kernel, not a live trading UI or entity integration. Profession assignment, later recipe reuse/replenishment and village/world lifecycle are deferred. It does not include later-version reputation or difficulty pricing.
