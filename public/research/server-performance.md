# Dedicated server tick time with many mobs (batch 74 mpperf74)

Measured with `node tools/bench-server-mobs.mjs` (executed, node 20, Apple Silicon Mac under load average 10-13 from parallel tracks, so absolute numbers are noisy by about 20%). The script builds a flat 116 x 116 world, two survival players 25 blocks apart, N persistent mobs (zombie, skeleton, pig, cow, sheep, chicken, creeper, spider, villager; seeded positions), natural spawning off, 20 warm-up ticks, then 200 timed ticks of `DedicatedSimulation.tick()`. Phases are wrapped method timers. Native target: 50 ms per tick.

(Some mobs die in the first ticks: zombies kill villagers, creepers blow up, so the live count is a little under the request.)

Phase split at 600 mobs: `mobs.entities.tick` (the mob loop, `tickMobs`) is 94% of the tick, `mobs.track` (the server tracker and packet queue) 3%, dispensers 0.7%, weather 0.4%, everything else (containers, chunk views, items, vehicles, falling blocks, pistons, serialising the tick message) under 0.2% each. Chunk streaming makes no measurable difference. Cost grows faster than linearly (100 to 300 mobs: 3x, 300 to 600: 3x).

CPU profile at 600 mobs (`node --cpu-prof`): `EntityMobs.push` (collideWithNearbyEntities) is about 34% of the run (inlined into `tickMobs`), the line-of-sight walk `rayTraceBlocks` about 12%, GC 5%, AI ticks about 2% each. `push` scans the whole entity list for every mob (O(n^2)), with a 12-block reject before the box test.

## Changes (no behaviour change)
- `src/projectiles.js`: `rayTraceBlocks` no longer builds closures for the NaN tests, and `rayBounds` uses a Set instead of an array literal built on every call. Same arithmetic, same results.
- A seeded determinism check (`node tools/bench-server-mobs.mjs --state`: 300 mobs, 150 ticks, `Math.random` replaced, mob state and packet hash every 50 ticks) gave identical hashes before and after: `946bf454b2ab7503 f8ea0cd95773e9c5 7f8b6da45ddf1a7a`.
- Gain is within the noise of the loaded machine (self time of `test` + `rayTraceBlocks` fell from about 1035 ms to 707 ms over a 150 vs 100 tick profile, per tick about 7.0 ms to 7.1 ms: no real change). Honest result: the 600 mob tick is already under the 50 ms target, and no large exact win was found.

## Batch 75 mppushgrid75: push grid (no behaviour change)
- `src/push-grid.js`: during the mob loop `EntityMobs.push` takes its candidates from 8-block cells (the entities within 12 blocks, the old reject, in exactly the order `entities` lists them) instead of scanning the whole list. Used from 200 entities up; smaller scenes keep the plain scan (measured: no gain at 100 and 300 mobs).
- Staleness guard: the grid is built at the first push of a loop and dropped when the loop ends; push re-files the mob, its mount and its rider; `markMoved` (seat in the loop, `endRidden`, `setLocationAndAngles` = dismount) re-files an entity moved off its own turn; a changed list length or a list slot that no longer holds the bucketed entity falls back to the full scan. `MC_PUSHGRID=off|verify` (and `pushGridConfig.mode`): `verify` runs both and throws on the first difference.
- Determinism (`--state`, now with `--seed --mobs --riders --pistons --rseed`) identical before and after for six scenes: default `946bf454b2ab7503 f8ea0cd95773e9c5 7f8b6da45ddf1a7a`; seed 3 / 200 mobs; seed 11 / 500 mobs / 20 rider pairs / 25 pistons; seed 5 / 120 / 10 / 10; seed 21 / 600 mobs; seed 8 / 40 / 6 / 8. Also identical with `MC_PUSHGRID=verify`.
- Measured (same machine, load 20-45, paired runs one process at a time, chunkStream on, 600 mobs): off 24.1, 24.8, 24.5 ms/tick; on 18.0, 18.3, 18.7 ms/tick (about 25% less). 300 mobs: 7.5 / 7.4 ms (the grid is not used below 200 entities, so no change), 100 mobs: unchanged. Several other runs were swamped by machine load (60+) and are not quoted.
- Profile after (600 mobs): `push` plus its inlined scan fell from about 3.3 s to about 1.2 s over 150 ticks; what is left is `rayTraceBlocks` / `test` (about 15%, line of sight), `tickMobs` itself, and GC.

## Not done, and why
- A spatial grid for `push` would cut the biggest cost, but it must keep list order and the exact candidate set. Entities are moved off their own turn (riders, pistons, carts, teleports, spawns and removals during the loop), so a grid needs a staleness guard that was judged too risky for a no-behaviour-change batch. Next step if 600+ mobs ever exceeds 50 ms: a per-tick grid keyed on (entities array identity, length) with a rebuild on any change and a brute-force check mode run against the existing mob-collision tests.
- Other per-mob box queries (`ai.nearby`, `nearby` player scans, the single-player player push at `entities.js` `serverPlayerUpdate`) did not show in the profile above 2%, so they still scan.
- Not measured: wire cost on a real socket, clients, mobs spread over several loaded areas with 10+ players, the Nether and End worlds, natural spawning cost with the cap reached (`spawnPass` ran only when spawning is on).

## Line-of-sight walk (batch 76 mplos76)
- `rayTraceBlocks` (projectiles.js) is the walk behind `EntitySenses.canSee`, arrows, explosions and fishing. The old body is kept as `rayTraceBlocksReference`; the live one is the same cell walk with the closures and the working array gone, the start vector in three locals, a direct read of the column's block array (only for a plain `World.get`, falling back to `world.get` for a non-resident column or an undefined cell) and an early `continue` for air. The stepping expressions are copied operation for operation, so every hit and null is bit-identical.
- `MC_RAYTRACE=verify` runs both on every call and throws on a difference; `off` uses the reference. `tools/bench-raytrace.mjs --scene=air|flat|mixed` verifies and then times both interleaved.
- Per-tick caching already matches native: `canSee` caches per target in `senseCache`, cleared once per AI tick (ai.js tick, entities.js think paths). The 600-mob bench casts about 2400 rays/tick, about 72 cells per ray; these are real native queries (target tasks, creeper swell, attack tasks), so the count was not reduced.
- Measured (executed, load average 10-13 so server ms/tick pairs were noise): CPU profile of the 600-mob bench, ray-walk self time 740 ms -> 446 ms over about 206 ticks (3.6 -> 2.2 ms/tick, share 15.9% -> 11.5%). Micro bench, us/ray reference -> fast: air 1.09 -> 0.77, flat 0.91 -> 0.67, mixed block soup 0.51 -> 0.45.
- Determinism hashes of two `--state` scenes identical before and after, also under `MC_RAYTRACE=verify`; 763 existing tests (projectiles, bow, fishing, explosions, fireballs, village fights, enderman, wither, buckets, server handlers, ai) pass under verify.

## Many players, the Nether and the End (batch 77 mpperf77)
- New bench: `node tools/bench-server-players.mjs --scene=over|nether|end --players=N --layout=spread|cluster --mobs=M [--ticks --warm --state --cpuprof=file]` (scene builder `src/mpperf77-scene.js`). Overworld: flat 200 x 200 field, survival players on a grid (spread) or within 8 x 8 blocks (cluster), mobs seeded near random players, natural spawning off. Nether and End: players travel through `dimensions.arrive`, mobs seeded in that dimension (pigman, ghast, magma cube, blaze, wither skeleton; enderman beside the dragon and crystals). `--cpuprof` profiles only the timed ticks.
- Measured (executed, node 20, load average 10-110 from parallel tracks, so ms/tick is only indicative; shares come from CPU profiles): about 300 mobs, ms/tick 8 / 16 / 32 players, spread 16.4 / 17.0 / 18.6, cluster 15.3 / 14.7 / 17.4. Nether 8 players / 200 mobs 11.6, 16 players clustered 12.8. End 8 players / 40 mobs 3.4. Wire grows linearly with players (14 / 50 / 113 KB per tick at 8 / 16 / 32). Players add little server time next to the mob loop (`mobs.entities.tick` is 70-85% of the tick in every scene); chunk views are idle after the join (End 0.3-1 ms while columns stream).
- Top self-time (32 players): Overworld spread: `relightSteps` 9% (creeper craters, lighting.js `update` per changed cell), `tickMobs` 5%, `track` 5-6%, ray walk 5%, villager zombie-avoid `nearby` + `canSee` about 7% inclusive. Cluster: `EntityMobs.push` 17%, `tickMobs` 10%, `track` 4.5%. Nether: `relightSteps` 11% (ghast fireballs), `tickMobs` 7%, `push` 7%, `sweep` fireballs 2.5%. End: `encodeColumn` 11%, redstone-live `scan` 10% (small, 0.2 ms/tick).
- Changes (`src/mpperf77-fast.js`, `MC_MPPERF77=on|off|verify`): (1) the villager zombie-avoid test (`villager.js` AvoidEntity.shouldExecute) cast a line-of-sight ray for every zombie in the world before the box test; `ai.js nearbyLate` runs the box first (native: getEntitiesWithinAABB then canSee), inclusive share 7.3-7.4% -> 1.5-1.8% (spread, 2 profile pairs), 3.4-3.9% -> 1.4-1.7% (cluster). (2) `ServerMobs.track` state resend walks each entry's watcher set instead of every (view, entry) pair (`stateDiffs`); small (about 1.5 points of self time, within noise at 32 players). (3) `push` box test without the per-candidate `pushBox` and size arrays (`pushMeets`, `sizeInto`); not measurable over the noise (push 6.8% -> 6.5%). The push O(n^2) in dense clusters remains.
- Determinism: `--state` hashes identical in the original source (git archive of HEAD), `on`, and `verify` for four scenes: over 32 spread / 300 mobs `cc079fadcf61b499 0674ce85c156330a 58299b4bff9fe5e0`; over 16 cluster / seed 4 `8bd0e5d3618f466e e94400f943582ba5 91ab1560f95052a9`; nether 8 / 200 `0a18d8b840c82191 02e40157ad563a46 52cf735557135ba7`; end 6 / 40 `920aa9156f3d1142 204de75dddd925c2 deb51d9f1a031c05`.
- Not done: batching lighting relights after explosions (the top self-time item in two scenes). Sequential per-cell 31 x 31 relights read neighbours that a later relight may still change, so a union-box relight is not provably identical; needs a verify-by-array-compare study. Also open: tighter push reach (slime size is unbounded, so the 12-block reject is already a bound only for normal mobs), chunk column encoding cost on join.

## Dense-cluster push and real sockets (batch 78 mpperf78)
- Push: `tools/bench-push78.mjs --mobs=N --pen=P --kind=a,b,c [--mode=on|off|verify] [--state]` puts N mobs in a P x P pen beside one player (`src/mpperf78-scene.js`) and times `EntityMobs.push`. The batch 75 grid hands back every entity within 12 blocks, which in a pen is the whole pen, so the per-pair work stayed O(n^2).
- Change (`push-grid.js` `FineGrid` / `pushNear`, `entities.js` `push` and `pushHalf`; `MC_MPPERF78=on|off|verify`, `MC_MPPERF78_MIN` default 60 entities): entities are filed in 2-block cells; a push only asks the cells that its box grown by 0.2 plus the largest half width in the grid can reach (half width bound = table width x slime size / 2). Entities wider than 6 blocks (huge slimes) and types without a table entry sit in an always-included list. The candidates come back in list order and the old tests (12-block reject, `pushable`, mount check, `pushMeets`) still run on them, so the same pairs run `applyEntityCollision` in the same order with the same float arithmetic. Filing is kept current by `markMoved` after every entity's own turn (`sections()` in `tickMobs`, which also covers the `continue` paths of squid, bat and ghast that never push), seat and dismount hooks, and push's own touch of the mob and its mount/rider.
- Measured (executed, node 20, load average 10-38 from parallel tracks, so indicative; push ms/tick of `EntityMobs.push`, pre-b75 scan -> b75 grid -> b78): 100 cows in 10 x 10: 0.40 -> 0.37 -> 0.16; 200 cows in 14 x 14: 0.96 -> 1.30 -> 0.24; 400 mixed animals in 20 x 20: 10.6 -> 13.3 -> 0.90; 600 cows in 24 x 24: 5.8 -> 8.5 -> 0.71; 120 zombie/spider/villager/horse in 10 x 10: 1.5 -> 1.4 -> 0.29. Whole server tick of those scenes 3.7 -> 2.6 ms (200 cows), 19.4 -> 5.2 ms (400 mixed), 13.8 -> 5.0 ms (600 cows). The b75 grid is slower than the plain scan in a pen (it sorts and rebuilds candidates and returns all of them); it still pays for spread-out herds.
- Determinism (executed): `bench-push78.mjs --state` hashes (120 ticks, seeded Math.random) equal between `MC_PUSHGRID=off MC_MPPERF78=off`, `on` and `verify` (plus `MC_PUSHGRID=verify`) in four scenes: 200 cows `56f75cbea3d3aff2`; 400 pig/sheep/cow/chicken `b68e8e324669941c`; 120 zombie/spider/slime/villager/horse `fff3d45b1d46fd2a`; 300 cow/ghast/giant/iron golem (mobs die in it, 272 left) `cce4f66095b4eaa7`. `verify` compares the filtered candidate list with the full scan on every push and throws on a difference.
- Real sockets: `node tools/bench-sockets78.mjs --clients=8..16 --mobs=N [--pen=P] --secs=15` starts `createDedicatedServer` (port 0, 127.0.0.1, temp data dir and accounts, flat 200 x 200 world, survival, natural spawning off) in-process, registers the accounts, and joins the clients from a forked child process over real `ws` WebSockets (join with `chunks: true`, input at 20 Hz, random walking, keep-alive acks). It wraps the 50 ms tick callback (everything the real timer runs), `simulation.tick`, `JSON.stringify` inside the callback (encode) and `WebSocket.prototype.send` (frame and write); bytes come from the server's `send`. It prints, then shuts down the clients, the server and removes the temp directory. Nothing outside localhost is contacted; it is a bench, not a test file.
- Measured over 15 s after 3 s warm-up (executed, load 20-40, so absolute ms are indicative): 
  - 16 clients, no mobs: tick callback 2.2 ms mean (p95 3.3, max 5.5): simulation 0.9, encode 0.24, `ws.send` 0.42; 92 KB/s per player in 20 msgs/s (4.6 KB `tick` message each, which carries every player's state; 72% tick, 28% chunk bulk during the run including the join).
  - 8 clients, 200 mobs spread over 60 x 60: 11.9 ms mean (p95 31.8, max 176; simulation 10.1, encode 0.33, send 0.72), 131 KB/s per player, 80 msgs/s per player. 16 clients, 200 mobs: 12.3 ms (p95 27.8, max 126; simulation 8.7, encode 0.82, send 1.15, rest 1.7), 179 KB/s per player, 82 msgs/s, 2.2 KB/msg. Mobs: 147-164 remain of 200 (night zombies and creepers). The wide p95 and max follow the machine load and the AI burst ticks, not the sockets.
  - 8 clients, 200 cows in a 14 x 14 pen: 4.0 ms (p95 6.3, max 13.4), 136 KB/s per player. 16 clients, 400 cows in a 20 x 20 pen: 8.0 ms (p95 13.3, max 15.1; simulation 5.8, encode 0.82, send 0.76), 292 KB/s per player, 45 msgs/s, 6.6 KB/msg (`mobs` packets are 56% of the bytes).
  - Ticks ran at 19.6-19.8 per second in every run (nominal 20), event-loop lag p95 under 12 ms; no client was closed.
- Reading: encode (`JSON.stringify` of per-player messages) is 0.2-0.8 ms per tick at 16 players, under 7% of the tick, and the socket write 0.4-1.2 ms; simulation time dominates. Bandwidth is the larger cost: 90-290 KB/s per player, from uncompressed JSON (`perMessageDeflate` is off), the `tick` message carrying all players, and `mobs` packets in dense scenes. Per-player JSON encoding is not shared between players because each message differs; a binary or delta format would be the lever and is not attempted here.
- Not measured: remote links (latency, Funnel/TLS), WebSocket compression, the live ledoge0 server (not touched), and clients that build the world (headless clients only parse and count).

## Profiles after batch 78, three small exact fixes (batch 79 mpperf79)
- Profiles (`node tools/bench-server-players.mjs ... --cpuprof`, node 20, load 10-15, 100 timed ticks): 16 players spread / 300 mobs 5.7-6.9 ms/tick, 32 players clustered 7.0-8.5, Nether 8 players / 200 mobs 8.5, dense pen (300 zombie/villager/cow/ghast) 6.8-7.5. The profile is flat: `tickMobs` (the mob loop with its inlined AI, move and push) 7-9% self and 54-61% inclusive in every scene; `walk` 21-35% inclusive, `track` 7-12%, `beforeMob` (nearest player) 5% at 32 players, pathfinding (`createEntityPathTo`) 4%, `collisionBoxes` (the block cell scan of getCollidingBoundingBoxes) 2-7%, Nether `sweep` (ghast fireball entity pass) 4.5% and `relightSteps` 5-6%. Pushes, line of sight and the tracker diff were already fixed in batches 75-78; no single item is above 10% self now.
- Changes (`src/mpperf79-fast.js`, `MC_MPPERF79=on|off|verify`; `verify` runs both paths on every call and throws): (1) `blockBoxes` (called from `entities.js collisionBoxes`) skips cells whose block id is 0 before calling the cell function (air has no boxes); the scan order and every pushed box are unchanged. Nether profile: `collisionBoxes` inclusive 89 -> 61 ms and `World.collisionBoxes` 57 -> 25 ms over 200 ticks. (2) `nearestView` (`server-mobs.js target`) loops over a cached array of the views (dropped by `addPlayer` / `removePlayer`) with the same first-strictly-nearest rule; `mobStateJson` builds the tracker state text from a 16-entry table of the dead/hurt/baby/burn flags for types with no other watched fields (the same key order, so the same JSON). (3) `sweepBox` (`fireballs.js sweep`) tests each mob against the swept query box with the same float arithmetic as `pushBox` and builds the box only for hits. Nether `sweep` 42 -> 47 ms (no change within noise), `sweepBox` itself 16-25 ms.
- Honest result: whole-tick differences are inside the noise of a loaded machine (32 clustered players 7.3-8.5 -> 7.0-7.3 ms/tick, 16 spread unchanged); only the Nether block scan shows a clear drop (about 30 ms of 1.2 s over 200 ticks, 2-3% of the tick). No large exact win was found; the mob loop is spread over many small costs.
- Determinism (executed, `--state`, seeded Math.random): hashes equal for `off`, `on` and `verify` in three scenes: over 16 spread / 300 mobs `8acbd1cd0713241d 7ae81414980108a6 93fd12209d442a43`; over 32 cluster / seed 4 `5a32d7a2589608c4 69ca4291d4f2db4b 394b7827cbe53507`; Nether 8 / 200 `0a18d8b840c82191 02e40157ad563a46 52cf735557135ba7` (also the hash recorded in batch 77). `src/mpperf79-b79.test.js` checks each function against its reference on random inputs plus a mixed pen under verify.
- Not done: pathfinding (`PathFinder`, 4% inclusive) and the `walk` body were not changed; they draw random numbers and read mutable state, so a cache needs a separate proof. `relightSteps` still belongs to the lighting tracks.
