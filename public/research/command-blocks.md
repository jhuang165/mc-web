# Command blocks (0.43.0)

Target: Java 1.7.10. Original block 137 maps to browser block 139/item 1139 (browser 137 was already an activator rail).
Obtain with `/give @p command_block`; native command blocks have no creative tab or ordinary block drops.
The original texture is used. The editor opens on use for a Creative player with command permission, has the 32767-character
command field, @p/@r/@a hints, previous output, Track Output toggle, Done and Cancel.

`tools/verify-command-blocks.mjs` checks the pinned client JAR and javap of BlockCommandBlock (akb), CommandBlockLogic (agp),
ServerCommandManager (bl), and GuiCommandBlock (bfh); the [reference](command-block-reference.json) records the bytecode hashes.
This is inspected bytecode evidence, not integrated native server execution. Port regressions exercise the live World/redstone
adapter, permissions, command effects, NBT comparison and chunk save/reload.

A rising power edge sets metadata bit 0 and schedules a one-tick update. Continued power does not repeat. A falling edge clears
the bit; a pending update still executes after power falls. The sender has permission level 2, its tile position, and default name
`@`. Player arguments resolve @p/@a/@r against the one local player; radius/name/mode/level filters are supported. Relative block
coordinates start at the sender. Commands that require an implicit player refuse a block sender. SuccessCount supplies comparator
input; Control NBT and browser runtime snapshots retain command, custom name, count, tracking and last output.

`commandBlockOutput` suppresses operator feedback; it does not suppress tracked timestamped output. Track Output suppresses that
stored output independently. Say/me broadcast to local chat. The integrated-server command-block enable option is treated as enabled.

Remaining adaptations: one local player (batch 13 added teams/scoreboard and `@p[team=,score_…]` selectors, [commands-b13.md](commands-b13.md)), no Java network server, styled HTML editor rather than pixel-exact
GuiCommandBlock, plain-text output represented as chat JSON, one success per command in the single-player adapter. Unsupported
commands still fail. Complete native server/command/selector parity is not claimed.

Batch 73 (docs sweep, 2026-11-14): "one local player" and "no Java network server" are first-release text. The dedicated server runs command blocks and command block carts (`multiplayer/server-cart-commands.js`, `server-owners.js`, batch 63) and has scoreboards and teams (`server-scoreboard.js`). Batch 80 (mpcmd80, 2026-11-18): the batch 73 line above was wrong for blocks. Until batch 80 the dedicated server ran only command block carts; a placed block kept its record (batch 79) but never ran. Now `installServerCommandBlocks` (`multiplayer/server-command-blocks.js`) gives every server lane (Overworld, Nether, End) the `BlockCommandBlock` behaviour, bytecode-read from `akb`, `aox`/`aoy` and `agp`. A rising edge sets metadata bit 0 with flag 4 and schedules a tick (tickRate 1). `updateTick` runs `agp.a(world)` (0 when `enable-command-block` is off) and then `updateNeighbourForOutputSignal`; the comparator reads the success count. The command goes through the cart runner (`runCommandLogic` in `server-cart-commands.js`). It uses the same supported-command table, the level 2 sender and the `commandBlockOutput` gamerule. The success count is 1 or 0, not native's selector match count. A tracked output (`TrackOutput`) stamps `[HH:mm:ss]` into LastOutput and marks the block for update. The client then gets the S35 action 2 compound of `agp.a(dh)`: Command, SuccessCount, CustomName, LastOutput (only when set) and TrackOutput, applied as `agp.b(dh)` reads it. `MC|AdvCdm` type 0 (`nh`, bytecode-read) is the GUI's Done button in multiplayer. It needs command blocks enabled, op level 2 (`mw.a(2,"")`) and Creative, it has no distance check, and it replies `advMode.notEnabled`, `advMode.notAllowed` or `advMode.setCommand.success`. Port differences are listed in `.shared-memory/notes/mpcmd80-b80-track.md`. These include: a player must be in the block's dimension for the command to run; the metadata change is still sent as a cell change; the cart setter's 8-block reach check is the port's own.

Batch 81 (mpcmd81, 2026-11-18), correcting batch 80's port differences:
- SuccessCount is now the run count. `CommandHandler.executeCommand` (`z.a(ac, String)`, bytecode-read) returns `j`, which goes up by one for each `processCommand` that does not throw. A username-index selector whose count is not 1 (`@a`, `c=` other than 1) runs once per matched player, so `/testfor @a` with three players stores 3 and the comparator reads 3. `@p` and `@r` are not expanded and count 1. The runner's new `count()` returns this number (`run()` is still `count() > 0`). Server blocks and carts, single-player blocks and carts, and the away replay all store it. A single-player world has one player, so its values do not change.
- A server command block runs with nobody in its dimension. Native `WorldServer.tickUpdates` needs only the block's own chunk, and the Overworld's spawn chunks (centre within 128 blocks of spawn, `unloadChunksIfNotNearSpawn`) stay loaded with no player online. The world hosts are now anchored on the block, not on the nearest player. That also fixes a b80 bug: `/summon ~ ~ ~` from a block used to resolve around the nearest player. Port limits: the server's finite Overworld is always resident, so a block outside the spawn area keeps running where native would unload it. Nether and End lanes still tick only with a player there; natively those dimensions keep no spawn chunks and unload once unwatched, so this is close.
- A server command block (or cart) that targets a player other than its base player (`/give`, `/tp`, `/gamemode`, `/xp` and so on through the server redirect) no longer fails with `commands.generic.exception`. `commandBlockSender`'s `playerName` was read-only, so the redirect's `Object.assign` threw.
- Command carts in the Nether and the End now run inside their dimension. Before, their queue was never drained.
- `MC|AdvCdm` type 1 (`nh.a(iz)`, bytecode-read) follows the native order. Command blocks off gives `advMode.notEnabled`. Without op level 2 and Creative it gives `advMode.notAllowed`. Then `getEntityByID` looks in the sender's own world and the entity must be an `xn`, else nothing is said. Then setCommand, `xo.e()` and `advMode.setCommand.success`. There is no distance check; the port's 8-block reach is removed.

Batch 82 (mpcmd82, 2026-11-18), correcting batch 81:
- `/spawnpoint <other player>` from a server block now sets the target's spawn at the target's own block. `CommandSetSpawnpoint` (`bp.b`, bytecode-read) calls the target's `mw.f_()` (getPlayerCoordinates), not the sender's. The port's redirect host kept the base player's `playerPosition`; `commandBlockSender` now gives the redirected host the target's position.
- The batch 81 limit "a block outside the spawn area keeps running where native would unload it" does not happen with the default spawn. The server Overworld is 128 × 128, so every chunk centre (8 to 120) is within 128 blocks of any spawn inside the window. `unloadChunksIfNotNearSpawn` (executed replay, `chunk-provider-reference.json`) never queues such a chunk, so native keeps the whole window loaded and ticking too. Columns can unload natively only when `/setworldspawn` puts the spawn at least 9 blocks outside the window. `DedicatedSimulation` option `residency: true` (`multiplayer/server-residency.js`, off by default) models that case. Scheduled redstone, fluid, fire and falling ticks run only in spawn-kept columns or in a column some Overworld player's managed view square covers. The note lists what is not modelled.
- Counts above 15: `akc.h` returns `getComparatorInputOverride` unclamped, and so do `akj.h` (an input of 15 or more is returned as is), `ahb.u` and `ahb.g`. Only `ahb.w` (getStrongestIndirectPower, which the wire uses) returns 15 for 15 or more (all bytecode-read). The port's engine already did the same. New tests check comparator to comparator (20), subtract mode (20 − 15 = 5), a comparator through a solid block (20), wire (15) and repeater (15).

Batch 83 (cmdblock83, 2026-11-18), correcting earlier batches:
- `/gamemode` from a block or cart no longer writes LastOutput. `ServerCommandManager.func_152372_a` (`bl.a(ac, aa, int, String, Object[])`, bytecode-read) sends the sender its copy only when `(flags & 1) != 1`, and CommandGameMode is the only caller passing 1 (every other notify goes through the 4-argument overload with 0). The ops still get `chat.type.admin` under the `commandBlockOutput` rule. The target's "gameMode.changed" line (S2B state 3, `gv` message table) goes to the target player; before batch 83 it also landed in the block's LastOutput when the target was the base player.
- A block running achievement, clear, xp, gamemode, kill, setworldspawn, spawnpoint or tp without a player argument now records `getCommandSenderAsPlayer`'s literal "You must specify which player you wish to perform this action on." (`y.b`, bytecode-read; a red ChatComponentTranslation of a key with no lang entry). It recorded `commands.generic.player.notFound` before. The scoreboard's two `y.b` calls are guarded by `instanceof` and never throw.
- GuiCommandBlock (`bfh.b`, bytecode-read) fills Previous Output with the command (`agp.i()`), then with LastOutput's `getUnformattedText` when LastOutput is not null. A block with no output now shows its command there; it showed nothing before.
- The client's comparator click prediction reads the client tile's SuccessCount from S35 (`akb.g` returns `agp.g()`); it read 0 before.
