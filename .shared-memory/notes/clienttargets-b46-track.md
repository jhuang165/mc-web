# Client hit targets beyond mobs (batch 46, branch batch46-clienttargets)

## Summary
- **Boats, minecarts, hanging entities, leash knots (executed).** `TrackerHitsProbe` lists the real `EntityBoat`, `EntityMinecartEmpty`, `EntityPainting`, `EntityItemFrame` and `EntityLeashKnot` in the client world double, with `attackEntityFrom` and `setFire` logged. The client `EntityArrow` finds each (all four classes' `canBeCollidedWith` is true) and `attackEntityFrom` answers **true** on a client world (`EntityBoat` and `EntityMinecart` return true under `isRemote`, `EntityHanging`/`EntityItemFrame` return true without acting). The arrow therefore plays `random.bowhit` and `setDead`s (the probe drops it like `World.updateEntities`), instead of ricocheting. None of them is an `EntityLivingBase`: no knockback, no thorns. The port: `ObjectTracker.attack` returns the target's `answers` flag, `Arrows.step` with `ctx.remote` ends the arrow on `true`.
- **Dragon parts (executed).** `EntityDragon.canBeCollidedWith` is false; the seven `EntityDragonPart`s are listed and collidable. `EntityDragonPart.attackEntityFrom` forwards to `attackEntityFromPart`, which is not remote-guarded: it redraws the dragon's target with three `Entity.rand` floats (the logged row carries the new target), clears `bD`, and returns true. So an arrow dies on a part exactly like on a boat. The three `rand` draws are not modelled (the port has no client dragon AI target). The port lists the client dragon copy's parts (`ClientEntity.dragon.parts`) with `reachesDragon` instead of its 16 x 8 box (the box was wrongly a target before).
- **Hooks (executed).** A hook's search hits the same entities. A true answer sets `field_146043_c` (hooked), but the follow and angler checks are under `!isRemote`, so the client hook keeps flying and hits again next tick (two logged calls on the recorded path, copy never removed). `FishHook` now sets `hooked` on a client only when the answer is true; nothing reads it there. `hookEnv.entities` now also honours `reach` (dragon parts).
- **Burning arrow (executed).** `EntityArrow.onUpdate` order: `isBurning()` (on a client: the S1C flag 0) and not an enderman, then `target.setFire(5)`, then `attackEntityFrom`. The probe's client cow gets `setFire` (fire becomes 100) before the logged attack; the enderman gets no `setFire`; a client boat gets `setFire` then the true answer. Yet `Entity.onEntityUpdate` does `if (worldObj.isRemote) fire = 0` (bytecode-read, and executed by running the listed mobs' own `onEntityUpdate`: the counter reads 0 at every tick start), so the copy only shows the flame until its own next update. The port: `a.clientBurning` from the arrow's meta byte 0, `ObjectTracker.ignite` logs `call:setFire`, main.js sets `ClientEntity.fire`, `MobTracker.clientTick` zeroes it before each step, `mob-renderer.js` draws the flame while it is positive (not for fire-immune mobs).
- **Burning arrow velocity resync (executed, found while replaying).** A burning server arrow sends an S12 velocity packet (and the S15 that goes with the metadata change) because `onEntityUpdate`'s `fire % 20 == 0` calls `attackEntityFrom(onFire)`, whose `Entity.setBeenAttacked` sets `velocityChanged`. The client arrow's velocity is rewritten by the quantised packet (a 1e-5 drift in the recorded flight). `Arrows.step` now sets `velocityChanged` on every 20th burning tick (also for live server arrows, which were missing the resync).
- **Port limits.** The port has no client copy of boats, carts, paintings, frames or knots, so `main.js` lists the live ones (boxes `bb`; the knot box is `[x+0.25, y+0.5, z+0.25, x+0.75, y+1, z+0.75]` from two executed tiles). A packet-driven copy lags the live one by up to a few ticks. A client entity's `fire` is only modelled on mob copies (boats and others keep no flame).
