# Batch 52 dragoncopy track

## Summary

Branch `batch52-dragoncopy`, cut from 8cd3f1725 (release 0.80.0). No port code changed: the open items turned out to be already right or are execution gaps.

- **Client dragon copy body turn: already native, stale follow-up.** `ClientEntity.step` calls `dragonUpdate()` and then `turn?.(this)`, which for the dragon is `clientAfterMove` -> `clientBodyTurn`; `ender_dragon` is in `CLIENT_LEGACY_TURN`, so `legacyBodyTurn` runs over the tick's travel after `renderYawOffset = rotationYaw` (EntityDragon.onLivingUpdate's remote branch, then EntityLivingBase.onUpdate's legacy turn). The executed `flyDragon` and `dragonDeath` records (b45, `TrackerMountsProbe`, real `xa.h()` as client copy) already compare `renderYawOffset` per tick: removing `ender_dragon` from `CLIENT_LEGACY_TURN` fails both (tick 3: got -76.41 want -79.44). The comment above `CLIENT_PHYSICS_OFF` ("only the body turn runs after it") is correct. The batch 51 note's "skips the same legacy turn" was wrong for the client copy.
- **Dragon death-spin body yaw: executed.** `dragonDeath` (300 ticks, health to 0 at tick 60) replays `rotationYaw += 20` with `renderYawOffset` and the legacy turn per tick, 1e-9. The server dragon's spin (`dragon.js` line 356 plus the same `renderYawOffset = rotationYaw` then `legacyBodyTurn` in `dragon-mobs.js`) is the same arithmetic; the server-side tick order of a dying dragon is not run through `FlyTurnProbe` (the client record covers the arithmetic only).
- **Squid client copy, executed (`b52dc`).** `TrackerMountsProbe.moreOf` now records, besides the air, the isRemote half of `EntitySquid.onLivingUpdate` on the real client `ws`: squidPitch, squidYaw, squidRotation, tentacleAngle (each with its previous value), randomMotionSpeed and rotateSpeed (fields bp..bz) every tick of `flySquid` (140), `swimSquid` (160) and `squidAir` (340). `checkMore` in `src/tracker-mounts.test.js` replays them against `c.squid` at 1e-9; all match with no port change. Mutation: pitch factor 0.02 -> 0.03 in `squidLivingUpdate` fails 3 tests.
- **Removed mob health 0: documented, not changed.** The port keeps a removed mob as a corpse (health 0, death 20) until the end-of-tick filter in `entities.js` (`health > 0 || death < 20`), and `entity-tracker.js` (`c.dead = e.health <= 0`, the S1C health), the away and replay code read it. The old health is already kept in `e.removedHealth` for the creeper explosion and peaceful despawn (read by the b50/b51 replays). The villager cure (`entities.js` ~1830) and mooshroom shear (`mooshroom-golem-live.js` 88) also zero health without `removedHealth`; nothing reads a removed mob's health in those paths, so they were left alone.
