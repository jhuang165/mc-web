# savedorder4 (batch 56)

## Summary
- Chunk load order: a saved record's `ord` now follows the order a native reload gives, not the order of the first entity seen. `loadRanks(frame)` in `src/saved-order.js` ranks chunks as the executed login does: the world's spawn grid (MinecraftServer.initialWorldChunkLoad, 25 x 25 chunks, x outer, z inner, from `(spawn + k) >> 4`), then the player's own chunk (World.spawnEntityInWorld loads it first), then the view square (PlayerManager.addPlayer, x outer, z inner), then the player's mount. A chunk outside the frame is not loaded natively; the port keeps those after the loaded ones in the old first-entity order. `main.js save()` passes the frame (`world.worldSpawn` of the Overworld, the player position, `mobs.viewChunks`) as a 4th argument to `stampSavedOrder` (one-line edit); the away run passes none and keeps the old order. The player entity itself is appended after its chunk's entities when that chunk was not already loaded by the spawn grid, otherwise at the end of the grid chunks; the port has no list entry for the player, so this is only in the reference (`-1`).
- Stacked riders: the login reads the first `Riding` compound only (sg.a does not read a nested Riding), so for a player on a cow that rides a cart the cart is in no chunk (skipped by the writer, it is ridden) and in no file (only nested): it is gone after a reload (executed). `stampSavedOrder` now drops the records of the chain below a carrier from the saved lists (`lostMounts`; the live entities stay until the page reloads) and removes the carrier's `riding` link.
- Away run and the player's mount: no change. The task text said World.updateEntities skips ridden entities and ticks them through the rider; the bytecode says the opposite: it skips the RIDER (`sa.m != null`, mount alive, `sa.l == rider`, then `continue`) and ticks the mount, which updates its rider. A player leaves a dimension through ServerConfigurationManager.transferPlayerToDimension, whose removePlayerEntityDangerously only marks the player dead (bytecode-read: no mountEntity(null)); the mount stays in the old world and updateEntityWithOptionalForce clears its dead rider after its first update, so the away run ticking it (b43) matches. Only playerLoggedOut removes the mount (`removePlayerEntityDangerously(player.ridingEntity)`; the player file keeps it), and no away run follows a logout. The away run therefore still ticks a record saved with `playerRides` / `rider: true`; I tried excluding it and reverted (the b43 test pins the rolling cart).
- Non-mob entities above y 256: the loader has no height limit; executed b52so/b56so sections clamp to 15 and the port's loaders restore items, orbs, carts, arrows and TNT at y 255/256/300/400 and keep them (new test). Painting and frame survival and boats were run over 130 ticks at y 300 in the port: same as at y 100 (they pop or fall the same way). No code change.
