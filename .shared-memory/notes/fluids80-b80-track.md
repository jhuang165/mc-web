# fluids80 (batch 80): fluid and fire leftovers of batch 79

## Summary
- Thrown pearls, snowballs and eggs in lava: `Projectiles.step` now runs the fire part of `Entity.onEntityUpdate` (sa.C). Water zeroes the counter; a client world (`remote`) zeroes it every update; a server ball loses 1 per tick and sets `velocityChanged` on every 20th (attackEntityFrom(onFire) only runs setBeenAttacked); `handleLavaMovement` (the 0.25 box shrunk 0.1 at the sides and 0.4 at top and bottom, `fluids.js inLava`) sets `velocityChanged` and fire = max(fire, 300). No EntityThrowable subclass overrides these. Fire is saved and loaded (`serialize`/`load`), imported from a Snowball or ThrownEnderpearl `Fire` short (`java-projectiles.js`) and exported for the `projectiles` list (`region-export.js`). The tracker already sent flag 0 = fire > 0. `objectView` now sets `burning` from the client copy's watched flag 0 on thrown kinds, and `ProjectileRenderer` draws an `EntityFireRenderer` (0.25 x 0.25) over a burning snowball, egg or pearl (Render.doRenderShadowAndFire).
- Falling still fluids: a falling 9/11 (record without `flowing`) now lands as the still block with only the hardening check and no scheduled tick. `FallingBlocks.landSet` sets `world.staticLiquid` around the `set`, and the `Fluids` `onChange` hook runs `harden` instead of `added` while it is set. Falling 8/10 (`flowing`) still schedule their tick (water 5, lava 30) and keep their metadata, as natively.
- Fluid stacks: `sameStackItem` also compares `rawId`, so flowing (8/10) and still (9/11) fluid stacks don't merge in the inventory, item-entity combine, inventory transfer or anvil. Same-id stacks still merge.
- Region import Sign and MobSpawner: `readSignTile` (getString of any tag, missing is "", cut to 15) and `readSpawnerTile` (MobSpawnerBaseLogic.readFromNBT on a fresh logic through `cart-summon.js spawnerRecord`, then `spawnerJSON`). A missing EntityId now reads "" (it used to default to "Pig"), and a wrong-typed one reads as its toString. Absent gate groups now come back as the logic defaults instead of being left out. `spawnerRecord` reads EntityId with `getStringAny` too, which also covers MinecartSpawner.
- Item Fire: `ItemEntities.load` sets `e.fire` from the saved Fire, so a loaded burning item burns on. `serializeOne` writes the counter whenever it differs from what the export assumes (-1 after aging, else 0), so a ticked burning item saves its Fire.

## Follow-ups
- Only a browser can confirm: the fire overlay on a burning pearl or snowball (size, orientation, sprite animation) in single player and on a multiplayer client copy, and that it disappears when the server counter runs out.
- Arrows (`bow.js`) don't set `velocityChanged` on the lava hit (setOnFireFromLava's attackEntityFrom(lava)); EntityArrow overrides attackEntityFrom, so check that before changing it.
- Potions, experience bottles, fireballs and wither skulls keep no fire counter in the port. EntityPotion and EntityExpBottle are EntityThrowables and would burn the same way. EntityFireball is immune (isBurning false).
- A burning item in single player saves Fire, but the client-side item renderer doesn't draw a fire overlay on items. Not checked here.
