# trackerids b50 track

Branch `batch50-trackerids` from ca6a447bf (0.78.0 plus a test fix).

## Summary
1. One id counter and one HashSet. `EntityIds` (the world's `Entity.nextEntityID`) already numbered mobs, orbs, carts, boats and hanging entities; `ObjectTracker` now takes it (`new ObjectTracker(10, random, entityIds)`, main.js passes it) and an item, arrow, thrown entity, TNT, falling block, rocket or hook that has no id of its own takes the next number when the tracker first sees it (the spawn tick; without `ids` it counts from 1 << 24 as before). `MobTracker.shareOrder(other)` puts the object tracker into the mob tracker's `JavaHashSetOrder` (main.js does it each tick, `trackObjects`), moving entries it already has. Each tracker's `walk()` is then the entries of its own in the relative order of the one set. Both trackers' per-entity packet streams are unchanged.
   Not done: the two walks still run at their own places in the tick (mobs in `tickMobs`, objects in `trackObjects`), so the packets of a mob and an item of one tick are not interleaved in one queue; nothing in the port reads the cross-entity order of two copies' packets except the ordering below. The item id is taken at the tracker's first sight, not in the constructor, so a mob spawned later in the same tick than an item can get a lower id than the item.
2. Destroy one tick late. Bytecode-read: `MinecraftServer.v` calls `WorldServer.tick` (mt.b), `updateEntities` (mt.h), then `EntityTracker.updateTrackedEntities` (mn.a); a removed entity's S13 goes into `EntityPlayerMP.destroyedItemsNetCache` (mw.bN) and the player's `onUpdate` (mw.h) sends it at the start of its next update, so the client applies it one tick after the untrack. The port already delayed the destroy packet in `flush` but the mob tracker threw the copy away at once when the mob left the list. Now `MobTracker.dying` keeps the entry (as `ObjectTracker` did), the copy stays present and keeps stepping until its destroy is applied. Effects: a destroyed ender crystal copy stays in the client dragon's search for one more tick; `clientIfTracked` and the crosshair/arrow hit targets (main.js `clientTargets`, `vehicleTargets`) still see the copy for that tick. A removed boat or cart's copy is still hittable one tick (the `object-tracker-vehicles` far-boat test now expects that).
   Whether the flush lands in the same tick as the removal (a mob listed before the player in the entity walk) is not modelled: the player is first in the list in practice.
3. Client step order. `MobTracker.clientList` (a Set) is the client world's entity list: a copy joins it when its spawn packet is applied and leaves on its destroy, and `clientTick` (both trackers) steps copies in that order, not in entry creation order; riders still step right after their mount. Packets of several entries are applied in the order they were sent (`packetSeq`, a WeakMap stamp on each packet) instead of entry by entry. An entry created first but out of range spawns later and steps later.
