# Ring pistons and ring chest loot track (batch 41, branch batch41-ringpiston)

## Summary
- **Rim piston, executed native record.** `tools/probes/RimPistonProbe.java` and `tools/verify-rim-piston.mjs` run the unchanged 1.7.10 `World.getBlock`, `ChunkProviderServer.provideChunk`/`loadChunk` and `BlockPistonBase.canExtend` (executed, not only javap) and write `public/research/rim-piston-reference.json` (class hashes). Result: a piston read into a chunk that is not loaded makes the provider load the saved chunk (`L 1 0 1`) or generate it (`G 1 0`) and the chunk stays loaded; `canExtend` sees the real blocks (13 stone cells: false). Only with `loadChunkOnProvideRequest` off does it see air (true).
- **What the port does, and why no code change.** The neighbour update still reads an unheld chunk as air, so `canExtend` can only answer true where native answers false (air ends the line early; it can never refuse). That queues a block event, which waits (`LiveRedstone.eventActive`, batch 37) until the chunks within 14 blocks are held, then re-decides through `tryExtend`, which refuses the same lines natively would (13 cells, obsidian) without changing anything. So the end state is the native one; the only difference is a no-op event that natively is never queued. `src/ring-rim-piston.test.js` replays a ring world against an all-resident world for a 13-block line, an obsidian block in the unheld chunk, and a 9-block line that does move (nothing moves before the chunk is held; identical end rows, no moving tile, no event left). I did not add a synchronous chunk load: columns arrive from the worker or storage asynchronously, and the event wait gives the same result.
- **Ring chest loot (a real bug, fixed).** Generated chest loot sits in the population record and is handed over only when a column first becomes resident (`claimFreshColumns`, once-only: an existing tile is never refilled). `openChest` does `chests[key] ??= newChest()`, so a hopper or dropper in the window reaching across the chunk edge into a never-resident ring column made an EMPTY chest, and the loot was lost for good at the later hand-over. New `src/ring-chests.js` `seedRingChest` fills the tile (and any pairing neighbour) from the unclaimed record first, with the restore rule unchanged; `containerAt` calls `host.seedChest` before `openChest`, `main.js` passes it to `hopperTiles` (dispensers and hopper carts share that host). `StreamingPopulation.unclaimedRecord` returns the record or null once claimed (builds the cell if it fell out of the LRU, one-off, deterministic); `restoreChests` is now exported.
