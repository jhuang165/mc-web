# Dedicated beacon effects, rim piston, hopper wait, 16/17 imports (batch 44, branch batch44-beaconring)

## Summary
- **Beacon effects in the dedicated world.** `DedicatedSimulation.tick` now calls the singleplayer `tickBeacons` (`src/pyramid-live.js`) over the server's beacon tiles with every connected player: every 80 world ticks (`this.time % 80`) the pyramid level and sky check, then the primary/secondary effects for players inside the box (range `level*10+10`, up to the world top, duration 180 ticks, amplifier 1 when primary equals secondary at level 4). No new rule code. Each grant is added to the player's server `survival.effects` and queued in `player.effectsOut`; `server/server.js` sends it as `{type:'effect', id, amplifier, duration, ambient}` (S1D). **There was no potion-effect message in the multiplayer protocol before**, so this adds the one message, and `DedicatedClient` gets `onEffect` (the client file has no screen for it; nothing in the game applies it yet, same state as `signEditor`). `chooseBeacon` now uses `canSeeSky` (height map of light opacity, as `Chunk.canBlockSeeTheSky`) instead of a solidity scan, so glass over a beacon no longer blocks the sky.
- **Native evidence.** Reused `public/research/beacon-reference.json` (BeaconProbe runs unchanged `aoq.h`/`aoq.x` with recording player doubles; 245 effect, 52 range, 12 tick records). New `src/dedicated-beacon.test.js` replays them through the dedicated simulation: the range records for dx >= 10 at levels 1 to 4 (a player nearer would stand inside the pyramid) and the level 4 equal and different primary/secondary effect records, plus roof, glass, no-primary and broken-pyramid cases. No probe or verify script changed, so no reference was regenerated.
- **Rim piston: no code change, a narrower claim.** Native `BlockPistonBase.canExtend` reads the real blocks (chunk loaded on demand, executed in batch 41). The port reads an unheld chunk as air, so for a line that reaches the unheld chunk the answer is unknowable at queue time; the event must wait and `tryExtend` refuses later (same end state). Not queuing would be wrong: a pushable line would then never extend, since nothing re-runs the neighbour update when the chunk arrives. A synchronous load is not possible (columns arrive asynchronously). New test: a refusal decided inside held cells (obsidian beside the piston) queues no event, as natively, so the no-op event exists only for lines that really cross into the unheld chunk.
- **Waiting hopper: keep the wait, add a bound.** Bytecode-read: `TileEntityHopper` (`api`) gets the container from `api.b(World, x, y, z)`, which calls `World.getTileEntity` (`ahb.o`), which calls `getChunkFromChunkCoords` (`ahb.e`) and then the provider; there is no `blockExists` test. With the executed record that `ChunkProviderServer.provideChunk` loads or generates on demand, natively the hopper always sees the real container (not air or null as the task text assumed), so proceeding as if empty would be less native than waiting. Rule now (`containerPending` in `src/inventory-transfer.js`): a failed residency read ends the wait immediately (`ContainerResidency.reach` already returned true after a failure); otherwise a waiter (hopper above/target, or cart at a cell) waits at most `PENDING_LIMIT = 600` consecutive updates (30 s), then proceeds with the container absent (picks up items). The count is per waiter and resets as soon as the container is readable. Load is normally milliseconds, so the bound only matters for a worker that never answers. Tests added to `src/ring-hopper-wait.test.js`.
- **Imports saved at 16/17: documented, not changed.** Generation 16/17 conflates three things: terrain, quiet callbacks and the native-spawn rule (`nativeSpawnGeneration` is true for 16/17 and false for the 22/23 import pair). A save at 16/17 may be a port-created world (native spawn) or an old import. Moving it to 22/23 would change spawn selection for port worlds, and moving it to a new pair needs a new version number threaded through `java-world.js`, the region importer's override list, workers and the away plan, with no native record for a mixed save (already stored chunks quiet, unvisited ones with callbacks; the seam at populated neighbours is the unknown). The b31 evidence (a 6 x 6 jungle temple area populates differently at 22) shows the difference exists, but the b31 survey found zero generated powered-door chains, so what a 16/17 save loses is rare. Not bounded for this batch.
