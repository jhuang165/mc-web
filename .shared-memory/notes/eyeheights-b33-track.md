# eyeheights (batch 33)

## Summary
- New native table: `tools/probes/EyeHeightProbe.java` + `tools/verify-eye-height.mjs` -> `public/research/eye-height-reference.json`. It loads every concrete Entity subclass of the unchanged 1.7.10 JAR (95 classes incl. client particles), builds it through its (World) constructor on the MobMoveProbe world double where that works (56 classes, real width/height) and calls `Entity.getEyeHeight` (sa.g). The 39 that cannot be built there (horse, players, particles, lightning...) are allocated and asked with marker heights 1, 2, 3, which proves the formula only. Replayed by `src/eye-height.test.js`.
- Result: `Entity.g()` is 0.0 (carts, boats, items, paintings, frames, arrows, orbs, TNT, falling blocks, projectiles, ender crystal, dragon parts). `EntityLivingBase.g()` is height * 0.85 for every living mob, except `EntityWolf` (height * 0.8). Players: `EntityPlayer.g` 0.12 (also EntityPlayerSP / EntityClientPlayerMP), `EntityPlayerMP.g` 1.62 (constant, also while sneaking; the constructor sets yOffset 0, so its posY is the feet), `EntityOtherPlayerMP.g` 1.82. Player and mob sneaking/baby states only change `height`, not the formula.
- Port: `livingEyeHeight(type, height)` in `src/ai.js` (float product, wolf 0.8) is now what `Brain.eyeHeight`, `entities.js` (air/drowning eye, in-wall eye, three call sites) and `explosion-simulation.js` (Explosion.doExplosionA reads posY + getEyeHeight) use. Only a wolf's value changed.
- Player eye at the AI call sites. Bytecode-read: `EntityLookHelper.setLookPositionWithEntity` (tu.a(sa,F,F)) uses `e.posY + e.g()` for an EntityLivingBase and the box middle for anything else; `tu.a()` pitch uses the mob's own `posY + g()`; `EntityLivingBase.canEntityBeSeen` (sv.p) is a block ray from `posY + g()` to `e.posY + e.g()` with both virtual; `EntityAIWatchClosest` goes through setLookPosition with `posY + getEyeHeight()`. On the integrated server the player the mobs see is the EntityPlayerMP: posY is the feet and `g()` is 1.62. `PlayerView.eyeHeight` (ai.js) and `PLAYER_EYE_OFFSET` (enderman.js) were 0.12 (EntityPlayer's) and are now 1.62; `PlayerView.y` was already the feet. `enderman-live.js` passed feet + 1.62 as the player's y and then added the eye again; it now passes the feet. It also passed a teleport target with no `eye`, so `teleportToEntity` computed NaN (an enderman never teleported toward a far target in play); the target now carries `eye`.
- Native records changed accordingly: `EndermanProbe.java` FakePlayer returns 1.62 from `g()` (stands in for mw.g; the stare grid keeps its eye at 63.62 by putting the feet at 62.0, the teleportToEntity target is at feet 0.12) and `VillageFightProbe.java` P does the same. `enderman-reference.json` and `village-fight-b32-reference.json` were regenerated; the base and b31 village-fight records are byte-identical (no sight line involved). With the 1.62 eye the replay still has no divergence in all 22 b32 records, but one conversion fewer happens (7 to 6), so the aggregate floor in `village-fight-b32.test.js` (not a parity assertion) went from 7 to 6. `enderman.test.js`: the teleportToEntity success count is 17 (was 23 with the 0.12 eye); chase/stare fixtures use feet 0.12 so their eye (1.74) is unchanged.
- Cart behind a wall, in a real browser: the b32 harness never picked a cart because `/gamemode 1` is ignored in a fresh world (no cheats): survival reach is 3 and the cart was 3.58 away. `window.__mc.commandHost.setGameMode('creative')` works. Script `artifacts/b33-eyeheights/cart-wall.mjs`, result `cart-wall.json`.
