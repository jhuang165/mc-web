## Summary
- **Entry timing (goal 1).** New `src/tracker-birth.js`: spawn sites that gameplay then moves call `recordBirth(entity)` (a shallow copy); `ObjectTracker.create` builds the entry from `takeBirth(e) ?? e`, so the spawn packets and the first S12 carry the creation state (natively EntityTracker.trackEntity runs from spawnEntityInWorld). A boat or cart pushed on its spawn tick now sends S12(0,0,0) and then the pushed S12, as executed (boatGlide row 0). Opt-in: `Boats.spawnBoat(.., { born: true })` (used by `Boats.place`), `Minecarts.spawnChest/spawnCart/spawnEmpty(.., { born: true })` (used by `placeHeldMinecart`). Saves, summons, portals, dispensers and away worlds are not recorded (they set state after the constructor, as NBT loading does natively before spawnEntityInWorld). The replay test no longer pre-creates the entry: it calls `recordBirth` like a spawn site and lets `serverTick` list the entity.
- **Flags (goal 2).** `Boats.collide` sets `airBorne` on the boat (and the other boat when mutual); `Minecarts.collide` sets it on the cart and, cart against cart, on both; `Boats.attack` / `Minecarts.attack` set `velocityChanged` (after the dead check). Bytecode-read: `sa.g(DDD)` (addVelocity) sets `al` (isAirBorne); `sa.g(sa)` and `xl.g(sa)` call it; `xi.a(ro, float)` and `xl.a(ro, float)` call `Q()` (setBeenAttacked = `H`). Executed: the entry's reaction (`boatPush`, `cartPush`): an addVelocity at tick 4 (off the 3 tick beat) sends S12 + a look packet at once, `Q()` at tick 8 sends S12 at once. The ObjectTracker already read both flags; no change needed there. Explosions push with plain `+=` plus attackEntityFrom (so velocityChanged only), as natively.
- **boatFar (goal 3).** Not a port bug. Executed with an added trace: the entry untracks the boat at tick 71 (4-block re-check, last sent position / 32 as an int, 82 -> 81.5 blocks > 80), exactly where the port destroys it. The probe's player double (`TrackerProbe.PMP.d`) only logged the destroy into `sent`, and `TrackerItemsProbe.run` kept the client boat alive. The probe now detects the untrack (player removed from the entry's tracked set) and drops the client one tick later; the replay runs the full 80 ticks and asserts the destroy tick (71) against the executed client vanishing at 72. Regenerating the other tracker references (items, extras, hits, mounts) may change a row if one of their scenarios ever leaves range; not regenerated here.
- **Furnace and command cart (goal 4).** Executed `cartFurnace`, `cartCommand`: spawn S1C has [0,16,0] after [0,0,0]; fuel makes onUpdate write 16 = 1 (S1C [0,16,1] at tick 3, [0,16,0] at 12). The **client** copy's `xq.h()` is not guarded by isRemote, so it rewrites 16 from its own fuel (0) every update: the client flag never stays 1 (`ObjectClient.stepVehicle` now resets meta 16 each update, executed client rows). Command cart: watcher 23 (command) and 24 (last output as JSON), "" and "" at creation, `updateCommand` writes the command and `null` or the ChatComponentText as a JSON string (`"done"`, quotes escaped), only changed objects go in the S1C. Bytecode-read: `agp.a(fj)` (addChatMessage) calls `e()`, so output updates 24. `metaValues`/`read` carry both. Port approximation: it cannot tell whether updateCommand ran, so a cart with a command and no output reads "null", one without a command reads "".
- Fix found on the way: `sameStack` treated any two strings as equal (`a.id === b.id` both undefined), so a changed string watcher object never produced an S1C. It now requires objects.
- Goal 5 (client boat splash particles, full-physics ridden client boat/cart) not done.
