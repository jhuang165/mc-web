# Batch 35 track ticktree3: tickEnd integration test, per-write fluid notification, executed fluid and falling sequences

## Summary
- **tickEnd pinned by a real runtime.** `src/tick-tree-runtime.test.js` builds `createRedstoneRuntime` over a real `World` with `attachTickTree` and drives `tickWorldSystems` as `main.js` does: a lever powers a piston (it extends, stays extended, retracts; same per-tick timeline as the standalone `rt.tick()` path), and a queued note-block event only plays inside the tick. The piston and note tests fail when the `tickEnd` call is removed from `world-tick.js` (checked by mutation), so the 0.62.0 regression is now covered beyond the stub test.
- **Fluid writes notify per setBlock.** `Fluids` has a `writers` list called after each native-style write (place, level change, removal) in a run. `main.js` adds the redstone engine (`fluidChanges([[x, y, z, old, now]], true)`), so redstone hears each write before the next one, as `World.setBlock` notifies neighbours at once. The per-run `step` observer in `main.js` is gone. I found no native case where the order shows in cells (water and lava replace only non-solid cells; the redstone reactions are scheduled ticks that never tie with fluid delays, or power changes that no later read of the same `updateTick` depends on), so I record this as closer to native, not as a shown bug. A test shows per-write and per-run end in the same world, fluid list and redstone save for a dust/repeater scene. The away-world still passes batched `fluidChanges` (away-*.js not touched, owned by awayrun5).
- **Executed fluid and falling sequences.** `tools/probes/TickSequenceProbe.java` runs the unchanged `akr`, `ant`, `alw`, `akx`, `anh`, `ali` `updateTick` on the FluidProbe World double with `BlockFalling.fallInstantly` (akx.M) set, a 1000-per-tick list, and the real two-loop `WorldServer.tickUpdates` shape (take the first min(size, 1000) due entries out of tree and set, then tick them; bytecode-read `mt.a(boolean)`). 3 scenarios in `tools/tick-sequence-scenarios.mjs` (36 x 36 sand slab losing its support, 900 water sources at once, sand and gravel slabs falling into a water pool and a lava pool) each exceed 1000 due entries in a tick. `public/research/tick-sequence-reference.json` holds class hashes and per tick [taken, ran, taken-order hash, grid hash], final grid, pending entries and the world Random state; `src/tick-sequence.test.js` replays them through `attachTickTree`. The double is not the real WorldServer: only its list model is verified on the real class (TileTicksProbe); the old FluidProbe double runs each entry at once, which the real class does not.
- **Two port divergences found and fixed by that replay.** (1) A flowing water/lava cell whose entry was taken but not yet run looked "still" (no pending entry) to a neighbour update and was rescheduled; natively a flowing block has no such hook. `Fluids.inFlight` tracks taken-not-run keys. (2) Fluids write with `world.put`, so sand or gravel next to a fluid write was never scheduled: sand over a torch or plant that water replaces never fell. `attachTickTree` now adds a `Fluids.writers` listener that calls the new `FallingBlocks.changed` (the body of `watch`'s hook). `FallingBlocks.fallInstantly` (mirrors akx.M) exists for the replay; the game leaves it false. With both fixes all three sequences match native in every tick.
- **Powered TNT in population.** Not re-searched. The batch 34 search (14 seeds, 21 areas, 13 desert temples with unpressed plates) stands; still synthetic only.
