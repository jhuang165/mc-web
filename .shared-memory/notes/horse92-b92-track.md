## Summary
1. **Entity-list order of the released rider's push: the premise was wrong, the port was already native.** `Vehicle92Probe` (a real EntityPlayerMP, the unchanged `xi` / `xs`, `yz.ab`, `mw.h`, `mw.i`) runs the world loop with the player before and after the vehicle (a linked rider is skipped, a released player gets the real `mw.h()`), then the network tick's real `mw.i()` for the released player. The two orders give byte-identical rows. The push that moves the boat or cart is `mw.i()` -> `onLivingUpdate` -> `collideWithNearbyEntities`, which runs in the network tick after the world tick, whatever the list order. The port pushes after the vehicles, so the sneak tick (boat and cart, both server paths) now matches the record with no push dropped. No code change; the b91 test drop-hack stays in `horse91-b91.test.js` (its record had no player update), the new test replays the push instead.
2. **Mounting tick C0C.** The b91 claim that a forward key in the mounting tick arrives a tick late was a harness limit: the port already applied a C0C that follows the C02 (record `mountKey`, boat and cart, passes without a change). The real gap ran the other way: a C0C that arrives BEFORE the C02 is dropped natively (`mw.a(FFZZ)` does nothing while `ridingEntity == null`), but the port kept it and the first tick used it. `server-vehicles.js` `takeRideOrQueue` + `simulation.js` (input and the actions loop): mounted at arrival -> taken at once; not mounted with a C02 / interact queued -> queued behind it as `{ id, ride }` and read only if the player is mounted by then; otherwise dropped (`rideSeen` still set).
3. **Mob rider on a saddled horse (Horse92Probe, 9 scenarios: zombie and skeleton, saddled and not, steering and standing, with a rear).** Four port differences found and fixed:
   - `horse-live.js` `horseRideThink`: `wi.e(FF)` writes `prevRotationYaw` as well (`putfield A`), the port left it at the tick-start value.
   - `mob-riding.js` `endRidden`: **`sa.ab` never writes the rider's yaw or pitch** (it only accumulates, clamps and subtracts the half-delta fields `h` / `g`; no `putfield y/z`). The port added the half delta to `rotationYaw` / `rotationPitch`, so a mob rider drifted (+10 degrees on the first steering tick, +5 pitch). The application and the unread delta state are removed.
   - `mob-riding.js` `seatPosition`: `wi.ac` while `bM` (the PREVIOUS rear amount, `prevRearAmount`; `bL` is the new one) > 0 moves the rider 0.7 * bM back along `renderYawOffset`, 0.15 * bM up, and gives a living rider the horse's `renderYawOffset`. The mob rider's seat ignored rearing (the player seat in `horse-live.js` already had it).
   - `mob-riding.js` `endRidden`: `yl.ab` copies the mount's `aM` into a skeleton or wither skeleton when the mount is an `EntityCreature` (no health test, no rear needed). `NOT_CREATURES` moved from `entity-tracker.js` to `mob-riding.js` (tracker imports it).

## Found wrong in the batch 91 list
- "A forward key sent in the mounting tick reaches the boat a tick late on the dedicated server": harness limit, not a port gap (the C0C after the C02 already applies in that tick). The real gap was the opposite order (C0C first), now dropped.
- "The port always pushes after the vehicles while natively the push happens in entity-list order": the player's push is the network tick's, after the world tick, in either list order; the port's order is native.
- The b91 note and `mob-riding.js` assumed the rider turns half way with the mount (`updateRidden`); the bytecode and the record say it never writes the rider's rotation.
