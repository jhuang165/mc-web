# Batch 34 track ticktree2: redstone creation ids, observer granularity, backlog, generated TNT

## Summary
- **Redstone creation ids in saves.** `LiveRedstone.save()` writes the shared creation id as an 8th item of each `pending` / `deferred` tick (only while a `TickTree` runs, like `n` on fluid, fire and falling entries). `restore` keeps it (`entry.n`), `attachTickTree` already numbers by `e.n`, `region-export.js` passes it into the `redstoneTicks` runtime value so `tileTickRows` orders all kinds by one creation id at equal time and priority, and `sanitizeRedstone` (`world-import.js`) keeps the 8th item. 7-item (older) saves load unchanged.
- **Observer granularity.** Reading the port: fire edits go through `world.set`, whose redstone funnel (`LiveRedstone.installFunnel`) already notifies neighbours inside each run, so fire was never deferred. Fluids write with `world.put`, and the redstone side learned of them through `fluidChanges` after the batch. `TickTree.tick(clock, observers)` now accepts an optional `observers.step(name, changes)` called after every run that changed cells; `main.js` uses it for fluids only (`fluidChanges(changes, true)`), and the renderer batch (`observers.fluids`) still comes at kind switches, followed by `redstoneRuntime.flush()`. No difference in saved or run order was shown to exist (delays of fluid, fire and neighbour-induced redstone ticks never tie; see `region-import.md` Batch 34), so this is a tightening, not a fix of a shown bug. Native `Block.updateTick` for fluids is still bytecode-read only, I did not execute it or newly bytecode-read it this batch. Within one fluid run (several native `setBlock` calls) the redstone side still hears about the changes after the run.
- **Low border of an area import.** Not kept, with the reason in `region-import.md`: no chunk of the written save has a box that holds such a tick, a native save never holds one, and it has no observable effect. Counted in `report.ticks.outsideArea`.
- **Backlog above 1000.** `TileTicksProbe` has 2 new `sequence` scenarios (2600 and 3300 mixed-kind entries, unchanged `WorldServer.tickUpdates` on six consecutive world times; the 30 earlier scenarios are byte-identical, 32 in all, class hash unchanged). `tick-tree.test.js` replays them through `TickTree`. Block ticking itself is still not executed (all entries sit at y 300, as in batch 32).
- **Generated primed TNT.** Searched 14 seeds, 21 population areas (13 desert temples, 4 jungle temples, 4 swamp huts, villages and mineshafts alongside): all 13 desert temples keep their 9 TNT unprimed (the plate above is unpressed), no other structure places TNT, no powered TNT. Not fabricated.

## Follow-ups (proposed gap lines)
- Fluid runs still notify the redstone engine after the whole `updateTick`, not per native `setBlock` inside it.
- Fire changes reach the redstone engine inside the run (funnel); the renderer batch is per kind switch (render only).
- Ticks beyond the low border of an area import are not written (no chunk of the save can hold them); counted only.
- The away-world still ticks its lists outside the shared tree (awayspawn track is moving it).
- Block ticking for a backlog above 1000 is replayed from the unexecuted-tick probe (entries at y 300); no executed fluid or falling tick sequence exists natively.
- No generated structure that primes TNT exists in 14 seeds (21 areas, 13 desert temples); powered TNT is only tested synthetically.
